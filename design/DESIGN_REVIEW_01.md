## 0. 총평과 개발 에이전트 코멘트에 대한 답

**S7을 먼저 보는 것이 맞다.** 상태 배지(`Tfz9o`)·에이전트 칩(`MmxsR`)·HITL 카드·질문 카드·시스템 메시지의 규칙이 전부 S7에서 정해지고 다른 화면은 그것을 재사용한다. S7은 SCREEN.md §4.5의 3열 구조, 상단 액션 5개, lane 카드 동작, 작성창의 트리거 미리보기 칩(× 버튼 포함)과 "새 lane으로 보내기" 토글, 우열의 종료 조건 진행률·"사람 승인 없이 완료됩니다" 경고·결정 기록·autonomy 표시까지 **명세의 문장을 거의 그대로 화면으로 옮겼다.** 특히 활동 피드 항목이 "에이전트가 [동사]를 [목적어]에 했다 → [결과]" 프레임을 지키고, run 헤더에 "Claude Code (ACP) · resume ✓"를 넣어 §11 지표(resume 성공률)를 눈에 보이게 한 것은 PRD의 의도를 정확히 읽은 것이다.

**배지 색 6종은 변수로 잘 정의됐다** (`$s-run` `$s-wait` `$s-block` `$s-pause` `$s-done` `$s-fail`). `paused`(#DB2777)와 `failed`(#DC2626)의 구분은 **충분하지 않다.** 색상환에서 27°밖에 떨어져 있지 않고 명도·채도가 같아서, 8px 점 하나로는 나란히 놓아도 헷갈리고 적록색약에서는 거의 같은 색이 된다. 그러나 배지가 항상 텍스트 라벨을 동반하므로 실사용에서 치명적이지는 않다. 권고는 §7에 있다 — 색을 바꾸기보다 **글리프(⏸ / ✕)를 배지에 넣어** 색 없이도 구분되게 하는 것이 낫다. 6색 팔레트에서 빨강과 90° 이상 떨어진 빈 색상 슬롯이 없기 때문이다.

## 3. PRD·SCREEN과 어긋나는 것

### C1. 에이전트 상태 배지에 lane 상태를 투영했다 (S9, S7 참여자 칩)

**문제.** PRD FR-1.3의 에이전트 상태는 `idle` / `working` / `waiting_human` / `error` / `offline` / `disabled` 여섯이다. `paused`와 `blocked`는 **lane 상태**(FR-6.2)다. 그런데 S9 카드에서 @Frontend는 `paused`, @QA는 `blocked` 배지를 달고 있고, S7 참여자 칩의 상태 점도 같은 색(`$s-pause`, `$s-block`)을 쓴다. 에이전트 하나가 lane을 여럿 가질 수 있으므로(FR-6.1) "이 에이전트가 blocked"라는 말은 정의되지 않는다 — lane #2는 blocked이고 lane #5는 running일 수 있다.

**왜 중요한가.** 범례가 "다섯 층이 같은 어휘를 쓴다"고 선언했는데, 이 어휘가 **층마다 유효한 값이 다르다.** 화면이 그것을 뭉개면 개발자가 에이전트 테이블에 `paused`를 넣는다.

**권고.** 에이전트 칩·카드는 FR-1.3 여섯 값만 쓴다. lane이 blocked인 에이전트의 상태는 `idle`(프로세스가 끝났으므로)이고, 그 사실은 lane 카드가 말한다. 참여자 칩에 "지금 무엇을 기다리는지"를 보여주고 싶다면 상태 점 옆에 **부가 텍스트**("lane #2 질문 대기")로 넣되 상태 값 자체는 바꾸지 않는다. 이 결정은 PRD/SCREEN에도 한 줄 필요하다 — "에이전트 상태는 lane 상태를 집계하지 않는다".

### C2. 세션 예산 초과인데 세션이 `active`다 (S7)

S7의 paused lane 카드와 HITL 카드는 "**세션** 예산 $20을 초과했습니다 (현재 $21.40)"라고 하는데, 헤더 배지는 `active · 2 running`이고 우열 비용은 `$3.20 / $20`이다. PRD FR-2.2·FR-7.3: 세션 예산 상한에 닿으면 **세션이 `paused`** 되고 HITL이 발행된다. 세션 예산이 초과됐으면 세션은 active일 수 없고, 비용이 $3.20이면 초과됐을 수 없다. 두 가지 중 하나로 고친다: (a) lane의 `budget_per_task` 초과로 바꿔 세션은 active로 두거나("task 예산 $2.00 초과 — $2.40"), (b) 세션 자체를 `paused · 예산`으로 바꾸고 우열 상단에 O6 배너를 그린다. **(b)를 권한다.** 그러면 빠진 paused 배너까지 한 번에 검증된다.

### C3. 예산 초과 HITL의 작성자가 에이전트로 표시된다 (S7, S8)

PRD FR-2.2·FR-7.3: 예산·시간 초과 HITL은 **플랫폼이 발행**한다(`source: system`, `task_id`만 채움). S7 HITL 카드는 "@Frontend · lane #3"이, S8 인박스 항목은 "@Lead:"가 작성자처럼 보인다. 작성자는 "시스템"이어야 하고, 어느 lane 때문인지는 부가 정보로 붙인다. 지금 표기는 "에이전트가 예산을 더 달라고 요청했다"로 읽힌다.

### C4. SCREEN §4.6 인박스 표의 `run_failed` 동작이 §4.5와 모순 — 캔버스가 맞다

SCREEN §4.6 표는 `run_failed`의 인라인 동작을 "재시도 / 세션 열기"라고 썼는데, §4.5는 "일반적인 재시도 버튼을 두지 않는다 — 항상 다시 지시"라고 한다. 캔버스 S8은 **"다시 지시"** 를 그렸다. 캔버스가 옳고 SCREEN §4.6 표를 고쳐야 한다. (SCREEN으로 되돌릴 항목)

### 6.2 컴포넌트화 부족 (Q1)

로컬 컴포넌트가 Badge·Agent Chip·App Nav **셋뿐**이다. SCREEN §5가 "같은 컴포넌트"를 명시한 **HITL 카드**는 S7과 S8에서 각각 손으로 그린 프레임이고 구조도 다르다(S7은 테두리 카드 + 3행, S8은 Head/본문/Actions). lane 카드 5장, 인박스 항목 6장, 메시지 카드, 조건 행, 프로파일 행도 전부 개별 프레임이다. 지금은 화면이 15개라 버티지만, O1~O10의 변형을 추가하는 순간 같은 카드가 20벌이 된다.

## 7. 상태 색 체계 판정

개발 에이전트의 질문에 대한 답이다.

**현재 6색의 색상환 위치**

| 변수 | 값 | 색상(hue) |
|---|---|---|
| `$s-fail` | #DC2626 | 0° |
| `$s-wait` | #D97706 | 32° |
| `$s-done` | #16A34A | 142° |
| `$s-run` | #2563EB | 221° |
| `$s-block` | #7C3AED | 263° |
| `$s-pause` | #DB2777 | 333° |

`paused`와 `failed`는 **27° 차이**이고 명도·채도가 같다. 8px 점으로는 나란히 두어도 헷갈리고, 1형·2형 색각 이상에서는 사실상 같은 색이다. 범례가 "paused — failed와 멀리"라고 써 놓고 색상환에서 가장 가까운 자리를 골랐다.

**색을 바꿔서 풀리지 않는다.** 남은 빈 슬롯은 142°~221° 사이(청록, 초록·파랑과 각 40°)와 263°~333° 사이(자홍, 보라·분홍과 각 35°)뿐이라 어디로 옮겨도 다른 상태와 붙는다. 6개 상태를 색상 하나로 구분하는 것 자체가 한계다.

**권고: 글리프를 배지에 넣는다.** Badge 컴포넌트의 `Dot`을 상태별 아이콘 슬롯으로 바꾼다.

| 상태 | 글리프 | 근거 |
|---|---|---|
| running | ● (또는 회전) | 그대로 |
| waiting_human | ⏳ | S7 카드 본문이 이미 쓴다 |
| blocked | ? | S7 카드 본문이 이미 쓴다 |
| **paused** | **⏸** | "멈췄지만 끝나지 않음" |
| done | ✓ | |
| **failed** | **✕** | |

그러면 색은 보조 신호가 되고, `paused`/`failed`는 색각과 무관하게 ⏸/✕로 갈린다. 추가로 `paused`를 **테두리만 있는 배지**(soft), `failed`를 **채운 배지**(solid)로 스타일을 나누면 "무게"(SCREEN §4.5 "실패는 크게")까지 표현된다. 색 자체는 그대로 둬도 된다. 굳이 바꾼다면 `$s-pause`를 청록(#0D9488, 175°)으로 옮기는 것이 그나마 낫지만, 글리프가 있으면 필요 없다.

이 결정은 SCREEN §9-1("디자인 토큰 먼저")의 범위이므로, Badge 컴포넌트 하나를 고치면 캔버스 전체 44개 인스턴스에 반영된다 — 개발 에이전트가 말한 변수 구조의 이점이 여기서 나온다.
