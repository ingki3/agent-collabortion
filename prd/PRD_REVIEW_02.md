## 0. 총평

v0.5의 가장 큰 개선은 **Buzz 개념을 우리 실행 모델에 맞게 번역했다**는 점이다. "HITL = 턴 종료, 재개 = 새 attempt"(FR-5.4), "취소는 `session/cancel`만 필요하므로 steering 능력 제거"(§8.2.1), "승인 토큰은 인증 세션 앞에서 의미 없음"(FR-5.4 주석)은 각각 왜 원안이 틀렸는지를 문서 안에 남겼다. 부록 B에 "채택하지 않은 것"을 항목별로 적은 것도 좋다. 다음 사람이 같은 실수를 반복하지 않는다.

lane과 작업 공간의 분리(FR-6.1)는 리뷰 #01의 제안(에이전트당 1:1)보다 나은 답이다. 격리 방식이 바인딩을 정하게 해서 시나리오 A(리서치 3-way 병렬)와 시나리오 B(워크트리 공유)를 하나의 규칙으로 설명한다. 재시도와 HITL 재개를 같은 코드 경로로 묶은 것(FR-7.1)도 구현 비용을 줄이는 결정이다.

남은 문제는 두 갈래다. 첫째, **수정한 규칙끼리 부딪히는 곳**이 있다. 합류를 한 번으로 통일했는데 §8.3 공통 규약은 여전히 "위임자에게 회신 멘션"을 요구하고, 취소 정책의 판별자를 "명시 멘션"으로 바꿨더니 에이전트끼리의 멘션도 남의 턴을 취소할 수 있게 됐다. 둘째, **v0.4의 잔재**가 §1.4, §2.1, §8.2.3, §8.2.4, FR-1.8에 남아 v1 범위와 어긋난다.

## 1. 새로 생긴 설계 충돌 (v0.5에서 발생)

### N1. 합류 1회 규칙과 §8.3 "회신 멘션" 규약이 충돌한다 (FR-3.3 규칙 4, FR-6.5, §8.3)

**문제**

- FR-3.3 규칙 4와 FR-6.5는 "자식 lane이 개별로 위임자를 깨우지 않는다. 합류는 한 번"으로 통일했다(M1 반영).
- 그런데 §8.3 "모든 에이전트의 공통 규약" 세 번째 항목은 여전히 **"남에게 위임한 일이 끝나면 위임자에게 회신 멘션을 남긴다"**고 지시한다. 회신 멘션은 명시 멘션이므로 규칙 2·4에 의해 위임자를 트리거한다. 결국 Lead는 자식마다 한 번씩 깨어나고 합류 때 또 깨어난다. M1을 프롬프트 한 줄이 무효화한다.
- 더 나쁜 경우: Lead가 `queue` 정책으로 자식 A의 회신 멘션에 깨어나 종합을 시작한 뒤 합류 `progress_update`가 오면, FR-3.4에 따라 큐잉되어 **두 번째 종합 run**이 돈다.

**권고**

- §8.3 규약을 "완료 보고는 `colab status set done --note`와 아티팩트 제출로 한다. 위임자를 멘션하지 않는다"로 바꾼다. 결과는 합류 묶음에 실린다.
- 서버 측 안전망: 자식 lane의 task가 자기 `delegated_from` 에이전트를 멘션하면 **게시는 하되 트리거하지 않고**, 합류 묶음에 그 메시지를 포함한다. FR-3.5의 서버측 억제와 같은 자리에 둔다.
- 합류 그룹의 정의를 명시한다: "같은 위임 task(`delegated_from_task_id`)에서 만들어진 자식 lane 집합". Lead가 두 번에 나눠 위임하면 합류도 두 번이다.

### N2. 에이전트와 일반 멤버의 명시 멘션이 남의 턴을 취소할 수 있다 (FR-3.4, FR-5.3)

**문제**

- FR-3.4는 "판별자는 하나다: 명시 멘션인가 아닌가. 작성자가 Director인지로 나누지 않는다"고 못박았다. Director의 암묵 라우팅이 턴을 죽이는 문제(리뷰 #01 C2)는 이걸로 해결됐다.
- 그러나 `mid_turn_policy`가 `restart-with-context`나 `interrupt`인 세션에서는 **에이전트가 쓴 명시 멘션**도 같은 정책을 탄다. QA가 작업 중인 Backend에게 "이 부분 확인해줘"라고 멘션하면 Backend의 턴이 취소된다. 에이전트 간 멘션은 사람보다 훨씬 빈번하므로, 이 정책을 켠 세션은 턴이 계속 끊긴다.
- FR-5.3에 따라 Director가 아닌 멤버의 메시지도 라우팅되므로, 워크스페이스의 아무 멤버나 멘션 하나로 진행 중인 턴을 취소할 수 있다.

**권고**

- 판별자를 두 개로: (1) 명시 멘션인가, (2) 작성자가 **Director(또는 deputy)인가**. 취소 계열 정책은 둘 다 참일 때만 적용한다. 에이전트·일반 멤버의 멘션은 정책과 무관하게 `queue`.
- 이 규칙은 리뷰 #01 C2에서 "작성자로 판별하면 안 된다"고 한 것과 모순처럼 보이지만 아니다. C2의 지적은 **암묵 라우팅**을 작성자 기준으로 취소하지 말라는 것이었다. 명시 멘션에 작성자 조건을 **추가로** 거는 것은 파괴적 동작의 범위를 좁힐 뿐이다.

### N3. 트리거가 어느 lane에 붙는지 정하는 규칙이 없다 (FR-3.3, FR-6.1, §7)

**문제**

- 데이터 모델은 `lane 1─N task`이므로 모든 task는 lane에 속한다. 그런데 FR-3.3의 규칙 1~7은 "task를 만든다"까지만 말하고 어느 lane인지는 말하지 않는다.
- FR-6.1 "위임 하나가 lane 하나를 만든다"는 `colab lane delegate`에만 해당하는가, Director의 멘션에도 해당하는가? 시나리오 A에서 Researcher가 lane 3개를 가진 뒤 Lead가 `@Researcher`를 다시 멘션하면 재진입할 lane이 셋 중 어느 것인지, 아니면 네 번째 lane인지 알 수 없다. "재위임은 기존 lane을 재사용한다"(FR-6.1)는 lane이 하나일 때만 결정적이다.

**권고** — 모든 트리거에 적용하는 lane 해소 규칙을 FR-3.3 끝에 추가한다.

1. 스레드 답글이고 그 스레드가 특정 lane의 task에서 시작됐으면 → 그 lane.
2. `colab lane delegate --lane <id>` 또는 `--depends-on`으로 명시했으면 → 그 lane.
3. 격리가 `worktree`면 → 그 에이전트의 세션 내 유일 lane(없으면 생성).
4. 그 외(`container`·`none`의 새 멘션) → 새 lane.

이 규칙이 있어야 `reentry_count`와 `done → running` 재진입이 결정적으로 동작한다.

### N4. task 상태 머신이 "재개 = 새 attempt" 모델과 맞지 않는다 (FR-7.1, FR-5.4)

**문제**

- FR-5.4·FR-7.1 본문은 재개를 "새 attempt, 같은 task 행, `attempt` 증가, 런타임 resume 우선"으로 정의한다. 그러면 재개는 다시 `dispatched → preparing(workspace 재사용) → running`을 거쳐야 한다.
- 그런데 FR-7.1 다이어그램은 여전히 `waiting_human ↔ running`을 직접 잇고 있다. "프로세스는 이미 종료되어 있다"(FR-7.1)와 양립하지 않는다.
- HITL 툴이 "턴을 끝내라"를 반환해도 에이전트가 따르지 않고 계속 작업할 수 있다. 그때 task 상태가 무엇인지, 한 턴에 HITL을 두 번 호출하면 어떻게 되는지 정의가 없다.

**권고**

- 다이어그램을 `running → waiting_human → queued`로 고친다. `waiting_human`에서 나가는 유일한 경로는 응답·기한 만료로 인한 재큐잉이다.
- 전이 시점을 명시한다: HITL 호출은 task에 `pending_hitl` 플래그만 세우고, **`turn_end`가 오면** `waiting_human`으로 전이한다. 턴이 끝나기 전에 게시된 메시지·편집은 그대로 기록한다.
- task당 열린 HITL은 하나로 제한하고, 두 번째 호출은 "이미 대기 중인 요청이 있다"로 거부한다.

## 3. Major — 구현 전에 정리할 것

### M1. 용어 충돌: "Workspace"가 두 가지를 뜻한다 (§3, §7)

Glossary에 **Workspace** 행이 두 개다. 하나는 최상위 테넌트(사용자·에이전트·런타임·세션을 담는 단위), 다른 하나는 작업 디렉토리다. 데이터 모델은 `workspace`와 `workspace_dir`로 구분하지만 본문(FR-6.1, FR-6.3, FR-6.4, FR-7.1, §8.4)은 그냥 "workspace"라고 쓴다. "워크스페이스 설정 `workspace_retention_days`"처럼 한 문장 안에 두 뜻이 같이 나온다. 작업 디렉토리 쪽을 **Workdir**(또는 "작업 공간")로 개명하고 스키마도 `workdir`로 맞춘다.

### M2. CLI 폴백 어댑터가 v1 범위인지 불명확하다 (§10, §12, §8.2.4)

v1 목록은 "런타임 2종: Claude Code(ACP), Hermes(ACP)"이고 CLI 어댑터는 없다. 그런데 §12 리스크 "ACP 어댑터 드리프트 → CLI 폴백으로 자동 강등(§8.2.4를 유지하는 이유)"과 오픈 이슈 1 "안정성이 떨어지면 Claude Code만 CLI를 1차로"는 Claude Code CLI 어댑터가 있어야 성립한다. 둘 중 하나다: (a) Claude Code CLI 어댑터를 v1에 명시적으로 넣거나, (b) v1은 ACP 단일 경로이고 드리프트 시 어댑터 버전 고정으로만 버틴다고 적는다. 스파이크 1의 결과가 (a)를 강제할 수 있으므로 v1 목록에 "조건부" 항목으로 적어두는 편이 낫다.

### M3. `.git/info/exclude`는 추적 중인 파일을 숨기지 못한다 (§8.4)

exclude는 **untracked** 파일에만 효과가 있다. 저장소가 이미 `CLAUDE.md`를 추적하고 있으면(대부분의 Claude Code 프로젝트가 그렇다) 마커 사이에 append한 순간 `git status`에 `modified`로 잡히고 에이전트가 커밋할 수 있다. 정확히 리뷰 #01 M6이 막으려던 상황이다. 추적 중인 파일에는 `git update-index --skip-worktree <path>`를 걸고 lane 종료 시 해제한다. 스파이크 5의 확인 항목에 "추적 중인 파일 케이스"를 추가한다. 또 에이전트가 작업의 일부로 `CLAUDE.md`를 정당하게 수정한 경우 lane 종료 시 복원이 그 수정을 지운다. 복원은 마커 구간만 제거하고 나머지는 보존해야 한다.

### M4. GC가 커밋 없는 워크트리의 미커밋 변경을 지운다 (FR-6.4)

"병합되었거나 **커밋이 없는** 워크트리만 자동 삭제"는 작업 트리에 미커밋 변경이 있어도 커밋이 없으면 삭제한다. 에이전트가 커밋하지 않고 diff만 제출하는 흐름(시나리오 B 4단계)에서는 이게 기본 상태다. 조건을 "병합되었거나, 커밋이 없고 **작업 트리가 클린한**" 워크트리로 바꾼다. 브랜치 삭제 여부도 정한다(워크트리만 지우고 브랜치는 남기는 편이 안전하다).

### M5. "지금 중단하고 다시 지시" 버튼의 대상과 입력이 없다 (FR-3.4, §6)

`interrupt`는 "새 메시지만으로 다시 시작"이므로 새 메시지가 필요하다. 버튼이 세션 화면에 하나 있으면 어느 lane을 멈추는지, 메시지를 어디서 받는지 정의가 없다. lane 보드의 각 running lane 카드에 버튼을 두고, 누르면 그 lane의 에이전트를 멘션한 메시지 작성창이 열리며, 전송 시 `interrupt`로 처리한다고 적는다. 메시지 없이 멈추기만 하는 "중단"은 별도 동작(`cancel` → lane `failed(cancelled)`)이다.

### M6. 서버측 빈 확인 메시지 억제의 판정 기준이 없다 (FR-3.5)

"본문이 짧고 멘션만 있으며 진행·결과·질문 신호가 없는 메시지"를 서버가 어떻게 판정하는가? §8.1은 "동기 API 경로에서 LLM 호출 없음"이므로 휴리스틱이어야 한다. 구현 가능한 기준을 적는다. 예: 멘션 링크를 제거한 본문이 80자 미만이고, `?`·URL·코드 블록·숫자가 없고, `colab status`·아티팩트 제출이 같은 task에서 없었으면 억제. 오탐 시 에이전트가 다시 멘션하면 된다는 문장은 그대로 유효하다.

### M7. `approval` 타입의 기한 만료와 deputy의 승인 권한이 미정이다 (FR-5.1, FR-5.2, FR-5.4)

- `--default`는 `question`·`choice`에만 있고 `approval`에는 없다. `autonomy: autonomous`에서 승인 요청이 기한을 넘기면 "proposed_default로 진행"할 값이 없다. **승인은 절대 자동 진행하지 않는다**를 명시해야 한다. 지금은 규칙이 비어 있어 구현자가 "거절로 간주" 또는 "승인으로 간주" 중 아무거나 고를 수 있다.
- deputy에게 "위임 알림"이 가지만 `approver_spec: director`인 요청을 deputy가 답할 수 있는지 없다. `director` spec은 "Director 또는 기한 절반 경과 후 deputy"로 정의한다.
- 기한 초과 시 (a) 대기 유지를 고르면 상태가 `expired`인데 여전히 답할 수 있는가? `open` 유지 + `overdue` 플래그가 더 정확하다.

### M8. `respond_to: nobody`가 실행 중·대기 중 task에 미치는 효과 (FR-1.9)

"이미 참여 중인 세션에서도 트리거를 중단한다"까지만 있다. 실행 중인 턴은 취소하는지(§8.2.2 절차), `queued` task는 `cancelled`로 보내는지, `waiting_human`의 열린 HITL은 남기는지 정한다. 킬 스위치라면 실행 중 턴도 취소하는 것이 맞고, 그 취소는 활동 피드에 "소유자가 정지시킴"으로 남긴다.

### M9. 예산 초과로 취소된 task가 재개 가능한지 (FR-7.3, FR-2.2)

턴 중 강제로 `failed(budget_exceeded)`가 되고 세션은 `paused` + HITL이 뜬다. Director가 "계속"을 승인하면 그 task를 **같은 재개 경로**(resume 우선)로 다시 돌리는지, 새 트리거를 기다리는지 없다. 전자를 명시해야 예산 컷이 작업을 잃지 않는다. `failed`가 아니라 `paused(budget)` 같은 재개 가능 상태가 더 정확할 수 있다.

### M10. `none` 격리에서 런타임 자동 선택이 resume과 충돌한다 (FR-2.1, FR-5.4)

`none`이면 `runtime_id`를 비울 수 있고 "온라인 런타임 중 자동"이다. 그러면 재개·재시도 시 다른 머신이 선택될 수 있고 `runtime_session_ref`는 무효가 되어 항상 콜드 스타트가 된다. task 단위 작업 공간(`none`은 lane당 폴더)도 다른 머신에 있다. **첫 task가 dispatch되는 시점에 세션 `runtime_id`를 고정**한다고 적는다. 그러면 `task`에 `runtime_id`가 없어도 된다.

### M11. 데몬 크래시 시 고아 런타임 프로세스 처리 (§8.2.2, §9)

"모든 종료 경로에서 프로세스 그룹 정리"는 데몬이 살아 있을 때 얘기다. 데몬이 죽으면 자체 프로세스 그룹으로 띄운 런타임은 살아남아 계속 파일을 고치고 `colab` CLI로 메시지를 게시한다. 그 사이 서버는 heartbeat 만료로 task를 재큐잉해 **같은 작업 공간에서 두 프로세스가 동시에 작업**한다. 데몬이 pgid를 디스크에 기록하고, 재시작 시 claim 전에 고아를 먼저 정리한다고 명시한다. `COLAB_TASK_TOKEN`은 재큐잉 시 폐기해 고아의 게시를 서버가 거부하게 한다.
