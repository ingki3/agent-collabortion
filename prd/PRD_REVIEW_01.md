## 0. 총평

이 PRD의 강점은 "무엇을 어디서 가져왔고 왜 바꿨는지"가 추적 가능하다는 점이다. 결정 로그(v0.2/v0.4 변경 요약), multica·buzz 코드 경로 부록, 런타임별 함정 표(§8.2.5)는 실제 코드에서 검증한 흔적이 보이고, 리스크 표(§12)도 솔직하다. 활동 피드 원칙(FR-7.2), approver_spec fail-closed(FR-5.4), 부재/장애 구분(FR-4.2), 고빈도 이벤트 비영속(§7)은 그대로 살릴 가치가 있다.

문제는 **Buzz에서 가져온 개념이 우리 실행 모델(사용자 머신의 CLI 프로세스)과 맞지 않은 채 들어온 곳**이다. Buzz는 YAML 워크플로 엔진 + Nostr 서명 이벤트 위에서 승인 게이트와 재개 지점을 정의하는데, 우리는 둘 다 채택하지 않았다(부록 B). 그런데 FR-5.4의 `resume_at`, 승인 토큰 해시, FR-3.4의 `steer`는 그 전제를 그대로 들고 왔다. 이 불일치가 아래 Critical 항목 대부분의 뿌리다.

또 하나는 **lane·런타임·격리 세 개념이 서로를 어떻게 구속하는지** 정의가 비어 있다는 점이다. 시나리오 B(워크트리 격리)를 문서의 규칙만으로 실행하면 여러 곳에서 막힌다(C3, C4).

## 1. Critical — 설계 결정을 바꿔야 하는 항목

### C1. HITL "일시 정지 → 재개" 모델이 CLI 런타임 실행 모델과 맞지 않는다 (FR-5.4, FR-7.1, §8.2)

**문제**

- FR-5.4는 "run이 결과를 반환하는 대신 일시 정지 상태로 넘어가고, `resume_at`(lane id + 다음 단계)부터 재개하며 처음부터 다시 실행하지 않는다"고 한다. "다음 단계"는 Buzz YAML 워크플로의 스텝 개념이다. 우리 에이전트 run은 CLI 프로세스 하나이고 스텝이 없다. 재개할 수 있는 유일한 수단은 **런타임 세션 resume**(ACP `session/resume`, `claude --resume`)이다.
- 그런데 §8.2.3·§8.2.5·오픈 이슈 4에 따르면 resume은 Antigravity에서 거부를 감지할 수 없고, Hermes는 유실 시 조용히 새 세션을 만들며, 프로파일 폴백 시 유실된다. 즉 "처음부터 다시 실행하지 않는다"는 보장을 지킬 수 없는 경로가 v1 런타임 3종 중 2종이다.
- `colab hitl ask`가 **블로킹인지 논블로킹인지** 정의가 없다. 블로킹(프로세스가 답을 기다림)이면: Antigravity `--print-timeout`이 끊고, Claude Code `--max-turns`·heartbeat(FR-7.1 3분 무응답 → offline)와 충돌하고, `max_concurrent_tasks`·워크트리·컨테이너를 최대 24시간(기본 기한) 점유한다. 논블로킹이면 위 `resume_at` 문장이 성립하지 않는다.

**권고**

- HITL 툴 호출 = **턴 종료**로 정의한다. 툴은 "요청이 등록되었으니 턴을 끝내라"를 반환하고, task는 `waiting_human`으로 전이하며 **동시성 슬롯을 점유하지 않는다**(명시 필요).
- 응답 시 **새 attempt**를 시작한다. 1순위 런타임 resume + "답변 + 승인 여부 + 사유"를 담은 턴 프롬프트, resume 실패·불가 시 브리프 파일 + 세션 히스토리 + 결정 기록으로 콜드 스타트. 오픈 이슈 4가 이미 이 검증을 요구하고 있다.
- `hitl_request.resume_at`을 삭제하거나 `runtime_session_ref`(런타임 종류 + 세션 id + provenance)로 바꾼다.
- 워크트리·컨테이너는 `waiting_human` 동안 보존한다(FR-6.4에 이미 "lane 종료 후 워크트리 보존"이 있으므로 정합).

### C2. `steer`의 정의가 두 곳에서 다르고, 기본값으로 두기엔 위험하다 (FR-3.4, §8.2.1, §8.2.6, §12)

**문제**

- FR-3.4의 `steer` = "진행 중인 턴을 **취소**하고 이전 지시 + 새 메시지로 재프롬프트". §8.2.1의 `steer(handle, message)`와 `capabilities.steering` = "진행 중 턴에 메시지 **주입**". 서로 다른 동작이다.
- 취소 + 재프롬프트는 ACP `session/cancel`만 있으면 되므로 `steering` 능력이 필요 없다. 따라서 "런타임이 steering을 광고하지 않으면 `queue`로 강등"(FR-3.4, §8.2.6) 규칙은 근거가 사라진다. 둘 중 하나로 정리해야 한다.
- 기본값 `steer` + FR-3.3 규칙 6("그 외 사용자 메시지 → assignee")의 조합: Director가 세션에 "좋아요, 계속해"라고 쓰면 assignee(Lead)로 라우팅되고, Lead가 실행 중이면 **그 턴이 취소된다.** 대화형이라는 이유로 기본값을 steer로 둔 것이 오히려 가장 흔한 상호작용을 파괴한다.
- 리스크 표(§12)의 "파일 쓰기·커밋 진행 중인 lane은 `queue`로 자동 강등"은 FR-3.4 본문에 없고, 데몬이 "되돌리기 어려운 작업 중"을 어떻게 판정하는지도 없다(마지막 tool_call이 edit/bash면? 그 뒤 몇 초?).

**권고**

- 용어 분리: 정책 이름은 `restart-with-context`(취소+재프롬프트) 같은 것으로 바꾸고, `steering` 능력(주입)은 그 능력이 있는 런타임에서만 쓰는 별도 정책 `inject`로 둔다. 또는 v1에서는 `inject`를 빼고 `steering` 능력 자체를 인터페이스에서 제거한다.
- 기본값은 `queue`로. 취소 계열은 **명시 멘션 또는 Director 메시지**에만 적용하고, 규칙 6의 암묵 라우팅 메시지는 항상 `queue`.
- "되돌리기 어려운 작업 중" 판정 기준을 FR-3.4에 적는다. 예: 마지막 `task_event`가 파일 편집·셸 명령이고 `tool_call_update`가 완료되지 않았으면 취소 보류.

### C3. Lane의 정체성이 정의되지 않아 워크트리 시나리오가 성립하지 않는다 (FR-6.1, FR-6.4, 시나리오 B)

**문제**

- FR-6.1: "여러 에이전트를 한 메시지에서 멘션하면 각 멘션이 별도 lane". 그러면 lane은 (세션, 에이전트)당 하나인가, 위임(멘션)마다 하나인가? 후자라면 워크트리 격리에서 같은 에이전트가 5번 멘션되면 워크트리 5개가 생긴다. 시나리오 A의 "Researcher에게 3개 항목 병렬 위임(lane 3개)"은 후자를, 시나리오 B의 "Backend/Frontend 병렬 lane"은 전자를 암시한다.
- 시나리오 B 4단계: "QA가 두 워크트리의 diff를 리뷰". QA는 자기 lane(자기 워크트리)에서 실행되는데 다른 lane의 워크트리에 어떻게 접근하는지 정의가 없다.
- 같은 단계: "Frontend에 수정 요청 → Frontend 수정". Frontend lane은 이미 `done`이다. 같은 lane을 재개하는가(상태 머신에 `done → running` 없음), 새 lane을 만드는가(새 워크트리 = 이전 수정 유실)?
- 데이터 모델의 `lane 1─N task`는 lane 안에 task 체인이 있다는 뜻이지만, 어떤 트리거가 기존 lane에 task를 추가하고 어떤 트리거가 새 lane을 만드는지 규칙이 없다.

**권고**

- **lane = 세션 내 에이전트별 작업 공간(1:1)**로 정의하는 것을 권한다. 위임·멘션은 그 lane에 task를 추가한다. 병렬성은 "여러 lane이 동시에 running"으로 얻고, 한 에이전트에 조사 항목 3개를 병렬로 돌리고 싶으면 에이전트 인스턴스를 3개 등록하거나(현재 모델과 정합) v1.1에서 lane 분기를 별도 설계한다.
- lane 상태 머신에 `done → running` 재진입을 추가하고, 워크트리는 lane 수명 동안 유지한다.
- 크로스 lane 읽기: (a) 리뷰어에게 다른 lane 워크트리 경로를 read-only로 브리프에 노출, (b) 또는 `colab artifact submit --type diff`를 강제하고 리뷰어는 아티팩트만 본다. v1은 (b)가 단순하다.

### C4. 런타임 자동 선택과 워크트리 격리가 양립하지 않는다 (FR-1.6, FR-2.1, 시나리오 D)

**문제**

- FR-1.6: `runtime_id`를 비우면 "해당 kind를 가진 온라인 런타임 중 자동 선택". 워크트리 격리는 `isolation.repo_path`가 있는 **특정 머신**에서만 가능하다. 같은 세션의 Backend lane과 Frontend lane이 다른 머신에 배정되면 시나리오 B의 QA 리뷰·병합이 불가능하다.
- 시나리오 D의 프로파일 폴백(Hermes → Claude Code)도 다른 머신으로 넘어가면 워크트리·아티팩트 디렉토리를 잃는다.

**권고**

- 세션에 `runtime_id`를 둔다. `isolation: worktree | container`면 필수, `none`이면 선택. 세션의 모든 lane은 그 런타임에서 실행한다.
- 프로파일 폴백은 **같은 런타임(머신) 안의 kind 전환**으로 제한한다. 다른 머신으로의 폴백은 `isolation: none`에서만 허용.
- 데몬이 `repo_path` 존재 여부와 git 상태를 `probe()`에 포함해 세션 생성 폼에서 검증한다.

### C5. 호출 권한 게이트가 세션 참여 모델과 충돌한다 (FR-1.9, FR-2.1, §9)

**문제**

- `respond_to: owner`(기본) + 형제 규칙 = "같은 소유자에게 귀속된 에이전트끼리만". 워크스페이스 멤버 A가 만든 Lead와 멤버 B가 만든 Researcher는 기본값에서 서로 위임할 수 없다. 팀 워크스페이스에서 기본값이 협업을 막는다.
- 권한 판정이 "체인 최상단 사람 originator" 기준이므로, Director가 소유자가 아닌 에이전트를 세션에 초대해 놓고도 자기 메시지로 트리거하지 못한다.
- 데이터 모델의 `agent`에 `owner_id`가 없다. FR-1.8은 인스턴스 필드로 열거하지만 스키마에는 빠져 있다.

**권고**

- **세션 참여 = 세션 내 트리거 허용**으로 정의한다. Director와 공동 참여자는 `respond_to`와 무관하게 세션 안에서 서로 멘션할 수 있다.
- `respond_to`는 "누가 이 에이전트를 세션에 **초대**할 수 있는가"와 세션 밖 멘션을 통제한다. `nobody`는 세션 안에서도 트리거를 막는 킬 스위치로 유지.
- `agent.owner_id`, `agent.respond_to`를 스키마에 추가.

### C6. v1 범위가 10주에 맞지 않는다 (§10)

**문제**

v1 목록에 다음이 전부 들어 있다: ACP 하네스, CLI 어댑터(Antigravity), 런타임 3종, 격리 3종(컨테이너 포함), 멀티 프로파일 편집기, `.agent.md` 가져오기/내보내기, Build with AI, `colab` CLI + MCP 서버, 활동 피드(렌더 클래스 7종), HITL 승인 토큰, 병렬 lane, 자동 종료 + 요약, 인박스. 이 중 컨테이너 격리와 Antigravity는 §12 오픈 이슈에 **아직 스파이크가 끝나지 않은** 항목이다.

Antigravity는 v1의 유일한 상시 CLI 경로다. 이것 때문에 하네스를 사실상 두 벌(ACP + CLI) 만들어야 하고, MCP 없음·비용 미보고·resume 거부 감지 불가·구버전 로그 파싱 폴백까지 §12 리스크 3건이 붙어 있다. 목표 6(벤더 혼합)은 Claude Code + Hermes 둘 다 ACP로 충족된다.

**권고 컷 라인**

| 항목 | 현재 | 권고 | 이유 |
|---|---|---|---|
| 컨테이너 격리 | v1 | v1.1 | 인증 전달 스파이크 미완(오픈 이슈 2). `none` + `worktree`로 시나리오 A·B 모두 가능 |
| Antigravity | v1 | v1.1 | CLI 어댑터 전체 + 리스크 3건. ACP 하네스 하나로 v1을 검증한 뒤 추가 |
| `.agent.md` 가져오기/내보내기 | v1 | v1.1 | 팀 팩과 함께. v1은 폼만 |
| Build with AI | v1 | v1.1 | 템플릿(FR-1.4)이 온보딩 목표를 대신함 |
| 활동 피드 | 중추 5 + 일반 + 원본 | 메시지·플랫폼 조작·파일 편집·셸·오류 + 원본 | 판단 근거 묶음은 이미 v1.1 |

이렇게 잘라도 10주는 빠듯하다. ACP 하네스 스파이크(오픈 이슈 1) 결과에 따라 Claude Code CLI를 1차로 되돌리면 하네스가 다시 두 벌이 되므로, 그 결정은 **1주차에** 내려야 한다.

## 2. Major — 구현 전에 정리해야 하는 항목

### M1. 합류(Join) 규칙이 두 곳에서 충돌한다 (FR-3.3 규칙 4, FR-6.5)

규칙 4는 "하위 lane 완료 보고는 위임한 에이전트를 깨운다"(lane마다), FR-6.5는 "모든 자식 lane 완료 시 `progress_update`로 결과 묶음 전달"(한 번). 둘 다 적용하면 Lead가 N+1번 트리거된다. 하나를 고르거나, 규칙 4의 개별 깨움을 `queue` 정책으로 병합해 FR-6.5 시점에 한 번만 실행되게 명시해야 한다. 자식 하나가 `failed`일 때 join이 나머지를 기다리는지도 결정 필요.

### M2. `user_approval` 종료 조건의 HITL 요청은 누가 만드는가 (FR-2.2, FR-5.4, §7)

시나리오 A 8단계 "종료 조건 1 충족 → Director에게 승인 요청"은 시스템이 발행하는 요청이다. 그런데 `hitl_request.task_id`는 필수이고 `approver_spec`, `resume_at`도 task 전제다. 시스템 발행 HITL의 스키마(`task_id` nullable, `source: system`)와 "나머지 조건이 모두 충족되면 플랫폼이 자동 발행"을 FR-2.2에 적어야 한다. 같은 표의 `criteria_met` "판정 에이전트"가 참여 에이전트인지 플랫폼 LLM(§8.1은 후자)인지도 통일.

### M3. `budget_reached` / `time_elapsed`는 종료 조건이 아니다 (FR-2.1, FR-2.2)

둘 다 `paused`를 만들 뿐 완료가 아니라고 표 자체가 말한다. FR-2.1 `limits`와 중복이다. 종료 조건 표에서 빼고 limits 절에서 "초과 시 paused + Director HITL"로 통합하면 조합 UI도 단순해진다.

### M4. 승인 토큰 모델의 위협 모델이 비어 있다 (FR-5.4, §7)

서버는 응답자 인증 + `approver_spec` 검증 + 멱등 저장을 이미 한다. 그러면 토큰 해시가 **무엇을 막는가?** "저장소가 유출되어도 승인을 위조할 수 없다"는 근거는 DB에 쓸 수 있는 공격자라면 `approved=true`를 직접 쓰면 되므로 성립하지 않는다. Buzz에서 토큰이 필요한 이유는 Nostr 서명 이벤트로 승인이 오기 때문이다.

토큰이 의미를 갖는 유일한 경우는 **로그인 없는 원클릭 승인 링크**(이메일·푸시)다. 그렇다면 링크 유출 = 승인이므로 1회성·짧은 수명·재확인 페이지가 필요하다. 결정 요청: (a) 원클릭 승인을 채택하고 토큰 수명·1회성을 명시, 또는 (b) 토큰을 제거하고 인증 세션 + 멱등 응답 레코드만 유지. (b)가 v1에 맞다.

### M5. 재큐잉·재시도가 부분 실행의 부작용을 무시한다 (FR-7.1, §9)

"heartbeat 만료 후 재큐잉", "2~3회 자동 재시도"는 파일을 절반 고치고 메시지를 두 개 게시한 task를 **처음부터** 다시 돌린다. idempotency key(task_id + seq)는 메시지 게시 중복만 막고 파일 편집·셸 명령은 막지 못한다. 권고: 재시도는 (1) 런타임 resume 우선, (2) 같은 lane 작업 공간 재사용, (3) attempt ≥ 2의 턴 프롬프트에 "이전 시도가 중단됨, 이미 게시한 메시지 목록, 현재 워크트리 상태 확인 지시"를 주입. C1의 재개 절차와 같은 코드 경로로 만들면 된다.

### M6. 브리프 파일 전달 경로가 모순되고, 워크트리를 오염시킨다 (FR-4.1, §8.4, §8.2.4)

- FR-4.1: "세 런타임 모두 시스템 프롬프트 인자 대신 이 파일로만 전달". §8.4: "ACP 경로에서는 [1]~[8]을 `session/new`의 시스템 역할로 한 번만 전달". 둘 중 하나다. ACP `session/new` 파라미터에 시스템 프롬프트 필드가 있는지 확인이 필요하다(§4 검증 항목). 없다면 ACP 경로도 지시 파일이 유일 경로이고 §8.4 문장은 삭제.
- 워크트리 격리에서 lane 디렉토리 = 저장소 체크아웃이다. 여기에 `CLAUDE.md`/`AGENTS.md`를 쓰면 (a) 저장소가 가진 원래 `CLAUDE.md`를 덮어써 프로젝트 규칙이 사라지고, (b) `git status`에 잡혀 에이전트가 커밋할 수 있다. 권고: 원본 뒤에 구분자를 두고 **append**하고 lane 종료 시 복원, 파일 경로를 `.git/info/exclude`에 등록. Claude Code CLI 폴백은 `--append-system-prompt-file` 계열 옵션이 있는지 확인해 그쪽을 우선.

### M7. "코드는 머신을 떠나지 않는다"는 주장이 사실이 아니다 (§9, §7, FR-4.3)

`task_event.input/output`에는 파일 편집 diff와 셸 출력이 들어가고, 아티팩트 타입에 "코드 diff"가 있다. 활동 피드가 "`runtime.rs`를 수정했다 (+12/−3)"를 펼치면 diff를 보여주려면 서버에 diff가 있어야 한다. 주장을 "소스 트리 전체는 머신에 남고, 에이전트가 읽고 쓴 내용은 활동 로그로 서버에 저장된다"로 고치거나, `task_event` 페이로드 마스킹·로컬 보관 옵션을 워크스페이스 설정에 넣어야 한다. 보안 검토 시 첫 번째로 지적될 문장이다.

### M8. 루프 상한 기본값이 너무 낮고, 빈 확인 메시지 억제가 프롬프트에만 의존한다 (FR-3.5, §8.3)

세션당 hop 20은 시나리오 B 한 사이클(PM→BE, PM→FE, BE→PM, FE→PM, PM→QA, QA→FE, FE→QA, QA→PM)에서 8을 쓴다. 정상 세션이 두세 라운드면 상한에 닿는다. 세션 누적이 아니라 **체인 깊이**(멘션 → 멘션 → … 연쇄 길이)와 **단위 시간당 hop 수**로 바꾸는 것을 권한다. 빈 확인 메시지는 서버가 "본문이 짧고 멘션만 있으며 진행·결과·질문 신호가 없는" 메시지를 트리거 없이 게시하는 휴리스틱을 검토할 만하다. 프롬프트 규칙은 어기는 순간 무한 루프다.

### M9. 예산 상한 강제 시점이 없다 (FR-2.1 limits, FR-7.3, §9)

세션 예산은 task 사이에서만 검사되므로 단일 task가 크게 초과할 수 있다. `--max-budget-usd`는 Claude Code CLI 폴백에만 있다. ACP 경로는 `usage_update` 누적이 task 예산을 넘으면 데몬이 §8.2.2 취소 절차를 밟는다고 명시해야 한다. `usage=false` 런타임은 추정치로 같은 규칙을 적용하는지도.

### M10. `supervised` 모드의 보류 메시지 상태가 모델에 없다 (FR-2.1, FR-5.3)

"Lead의 모든 위임 메시지가 Director 승인 후에만 전송"은 `message`에 `pending_approval` 상태가 필요하고, 그 승인은 HITL `approval`과 같은 객체여야 한다. v1.1 기능이지만 스키마는 v1에서 잡아야 마이그레이션이 없다.

### M11. `AskUserQuestion` 차단이 CLI 폴백에만 있다 (§8.2.4, §8.2.5)

ACP 경로(`claude-code-acp`)에서도 같은 툴이 호출되면 같은 문제가 난다. ACP에서 툴을 disallow하는 수단(어댑터 옵션, 설정 파일)을 스파이크 항목에 추가.

### M12. HITL "기본값 제안"이 CLI와 스키마에 없다 (FR-5.2, §12)

FR-5.2(b)와 리스크 표는 "에이전트가 제안한 기본값으로 진행"을 전제하는데 `colab hitl ask`에 `--default` 옵션이 없고 `hitl_request`에 `proposed_default` 필드가 없다. 리스크 표는 "강제"라고까지 썼다.
