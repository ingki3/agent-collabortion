- 바뀐 곳: [6] 만 43 · [6]+[7] 26 · [7] 만 1. [6] 은 아티팩트 줄(새 버전 제출마다 바뀜), [7] 은 결정 기록. 브리프는 ACP `_meta.systemPrompt` 로 가므로(`contracts.BriefACPMetaSystemPrompt`) **[6]·[7] 이 바뀌면 시스템 프롬프트가 달라져 재개 세션의 캐시 접두가 통째로 무효**가 된다. harness E12-11 은 [1]~[5] 의 바이트 동일만 지키는데, 캐시는 [8] 까지 한 덩어리로 본다.
- 캐시 TTL: 비용 적합에서 cache_write 단가를 입력의 **2배($10/M, 1시간 TTL)** 로 두면 claude_code 101 attempt(측정 비용 + usage 이벤트가 있는 opus-5 행)의 실측 비용과 **중앙 1.000**(p10 0.96)으로 맞고, 1.25배(5분 TTL)면 0.84 로 모자란다. 그래서 「5분 넘으면 만료」 가정은 이 런타임에 맞지 않는다. 1시간 넘은 브리프 동일 턴 1건만 TTL 로 설명된다.
- **재쓰기 비용**: 놓친 턴의 첫 호출 쓰기에서 새 턴 프롬프트 몫을 뺀 세션 재쓰기 **3,125만 토큰** — 적중했으면 읽기($0.5/M)였을 것을 쓰기($10/M)로 냈다 → **약 $297**(claude_code 세 에이전트 $1,199 의 25%).

H2 는 「간격이 원인」이라는 형태로는 **기각**, 「깨어날 때 세션 전체가 캐시 쓰기로 재청구된다」는 현상은 **확인**(원인은 브리프 변경).

1. **브리프 [6]·[7] 을 시스템 프롬프트 밖으로(턴 프롬프트의 `<room_artifacts>`·`<room_decisions>` 로)** — 브리프가 안 바뀌면 재개 턴 첫 호출이 적중한다(7턴 중 6턴). 이 방 기준 약 **$297 / claude_code 비용 25%** 가 대상이고, 코드 변경은 bundle.go 한 곳 + harness §10 의 [6]·[7] 자리(계약 변경 — Lead 결정 필요). E12-11 을 「[1]~[8] 전부 같은 방·같은 미션에서 바이트 동일」로 넓히는 것과 같다. 턴 프롬프트는 이미 매번 새로 쓰이므로 결정·아티팩트 목록을 거기 둬도 추가 비용은 그 줄 수뿐이다.
2. **재개 턴 델타**: 재개면 `<history>`·`<mission_messages>` 를 lane 이 마지막으로 본 메시지 뒤의 것만. 새 턴 프롬프트가 세션 증가의 55~58% 이므로 Lead 세션 증가 속도를 대략 절반으로 줄이고, 톱니의 평균 높이(=호출당 cache_read)를 같이 낮춘다 — 1단계 기준 「Lead 호출당 cache_read 중앙 −50%」의 본체.
3. **세션 크기 상한**: 지금은 1M 창 자동 압축(~97만)에서만 꺾인다. 예: 세션 시작 크기 30만 초과면 다음 task 를 계획적 cold start(새 세션 + 전체 프롬프트 한 벌). 깊이 2 턴이 이미 52만이므로 상한이 곧 「재개는 1~2턴까지」가 된다.
4. **판정은 새 계측으로**: 아래 §7 의 `task_context_metric` 이 attempt 마다 위 수치를 직접 남긴다 — 1단계 전후 A/B 는 스냅샷 재구성 없이 SQL 한 번이다.

hermes(Designer·Developer) 는 비용이 가장 큰데 캐시 쓰기 보고가 없어 이 보고서로 판정하지 못했다 — 계측이 쌓인 뒤 따로 본다.

## 7. 계측(운영 코드) — 이제 attempt 마다 남는 것

새 표 `task_context_metric`(마이그레이션 `00NN_task_context_metric.sql`, 번호는 PR 직전 dev 마지막 +1). 동작 변경 없음: 쓰기는 세이브포인트 안이고 실패해도 claim·heartbeat·finish 는 그대로(주입으로 증명). 계약 변경 없음(데몬 칸은 기존 finish/heartbeat 의 것만).

| 시점 | 칸 |
|---|---|
| claim (`queue/context_metric.go`) | 브리프 [1]~[8]·턴 프롬프트 블록별 `{bytes, tokens_est}`(`sections`) — ① history ② mission_messages ③ room_decisions/room_summary, trigger, folders, resumed, rebind, truncation_note, mission_progress, roster_status, respond 와 각 블록 안 작업 내용(`/detail`) 부분 · 줄 수(`counts`) · 번들의 resume 여부·session id · 같은 lane 직전 attempt 끝과의 간격(`gap_seconds`) |
| heartbeat (`tasks/context_metric.go`) | 턴 중 누적 `[경과초, cache_read, cache_write, input]` — 값이 바뀐 것만, 상한 240 |
| finish | `resume_outcome`, 같은 런타임 세션의 이전 턴 수(`session_depth`), input/output/cache_read/**cache_write**(task_usage 에 칸이 없어 버려지던 값), 도구 호출 수·종류(`tool_call_id` 단위, 권한 묻기 제외) |

첨부 줄(T-MEDIA #375)은 아직 dev 에 없다 — 들어오면 `<trigger>` 안에 들어가므로 `prompt.trigger` 에 잡히고, 따로 보려면 `prompt.trigger/attachments` 키 하나를 더한다.

예시 질의: Lead 재개 턴의 첫 호출 쓰기 비중 = `samples->0->>2 / (samples->0->>1 + samples->0->>2)` · 깊이별 세션 크기 = `session_depth, samples->0`.

## 8. 한계

- 세션 id 가 finish 의 ref 로만 남아 있어, 콜드 턴은 「같은 lane 의 다음 재개 턴이 그 id 로 재개했다」로 이어 붙였다(lane 당 ref 하나라 모호함은 없다).
- 「세션 시작 크기」는 첫 usage 이벤트가 API 호출 하나만 담은 턴(cache_read = 10,130 또는 적중)만 썼다. 첫 이벤트에 호출 둘 이상이 섞인 턴은 제외.
- 토큰 보정 2.53 은 쓰기 = 새 프롬프트 + 직전 턴의 캐시 안 된 꼬리라서 **상한**이다. 표본 5개가 좁게 모였다(2.41~2.60).
- 재생은 메시지·결정·아티팩트를 dispatch 시점으로 되돌리지만, 미션 진행도·참여자 상태·폴더 행은 사본 시점 값이다(프롬프트의 1% 미만).
- 비용 적합은 claude_code 모델(opus-5 계열)만. hermes 는 가격·캐시 보고 방식이 달라 제외.
- 회상 문항은 한 방·한 사본에서 에이전트가 고른 30개다. 문항을 고른 사람(나)이 채점도 했으므로, 2단계 판정 전에 다른 에이전트의 교차 채점 1회를 권한다.
