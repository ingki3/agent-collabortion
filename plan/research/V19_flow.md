## 1. Director 요구 ①~⑤ 대 PRD 조항 대조표

| 요구 | 충족 조항 | 판정 | 빠진 것 |
|---|---|---|---|
| **① 채팅방을 간단히 만든다** | FR-2.1(칸 하나: `name` + `description`), §3.1, §10 R2 | **충족(조항) / 미충족(화면)** | 만들기 화면이 §6 에 없다(Z-1). **만든 직후의 빈 방 상태가 정의되지 않았다** — `SCREEN.md` §7 은 빈 상태를 화면마다 못박는데 방에는 그 자리가 없다. 「무엇부터 하나」(초대? 메시지? 일?)를 아무도 말하지 않는다 |
| **② 참여자·에이전트를 초대한다** | FR-2.2, §7 `room_participant (agent_id? \| user_id?)` | **부분 — 모순 1건** | **(a) FR-2.2 "방장이 사람과 에이전트를 아무 때나 초대" ↔ FR-5.3 "세션에 '초대'라는 절차는 **사람에게 없다** — 에이전트만 참여자로 등록된다. 워크스페이스 멤버는 누구나 열람·게시".** §5 대응표가 "참여자·초대 → 방"으로 옮기라 하므로 두 문장은 같은 대상을 말하며 충돌한다. **(b) 「방장」이 FR-5.3 의 사람 역할 3종(Director·deputy·멤버)에 없고, `hitl_request.approver_spec` enum(`director \| any_member \| user_id`)에도 없다** — FR-2A.1 은 "일 밖 task 의 HITL 은 **방장**에게 간다"고 하는데 그 값을 저장할 칸이 없다. **(c) 초대 시 프로파일 선택·경고**(마법사 5단계가 하던 "선택한 런타임에 없는 `runtime_kind` 경고", `respond_to` 초대 불가 사유)가 FR-2.2 에 없다 |
| **③ 방 안에서 여러 일을 한다** | FR-2A.1~2A.6, FR-2A.5(「진행 중인 일」 칩), §7 `work` · `message.work_id?` · `lane.work_id?` | **부분 — 구멍 4건** | **(a) 메시지가 어느 일에 속하는지 사람이 정하는 수단이 없다**(§3 참조). `message.work_id` 는 nullable 칸만 있고 채우는 주체·규칙이 없다. **(b) 동시 일 상한**: FR-2A.5 는 "동시 실행 상한은 방 설정이 정한다"는데 FR-2.3 `limits` 칸은 「방 예산·시간·**동시 lane** 상한」뿐 — 동시 **일** 상한이 없다. **(c) 「이걸 일로」의 기본 종료 조건이 `artifact_submitted(assignee) AND user_approval` 인데 그 경로가 `assignee` 를 묻지 않는다**(FR-2A.1 기본값 목록에 assignee 없음, `work.assignee_agent_id` 는 스키마에 있음) → 여는 순간 S-84 와 같은 `blocked_reason` 상태가 된다. **(d) `work` 에 `deputy_director_user_id` 가 없다** — FR-5.2 의 deputy 는 "세션에" 붙어 있었고 §5 대응표는 Director 를 일로 보내는데 §7 `work` 행에는 deputy 칸이 없다 |
| **④ 방 맥락을 모든 에이전트가 공유한다** | FR-4.1(방 히스토리·결정 기록), FR-2.2(합류 이전 히스토리도 읽는다), §3 용어표 Shared Context | **충족 — 단 눈금 1건 미정** | 유일한 공백: FR-4.1 「방 히스토리 = **최근 N개** 메시지」. 세션은 끝이 있어 N 이 사실상 전체였지만 **방은 끝나지 않아 N 이 실제 절단선이 된다.** N 의 기본값·초과 시 무엇을 남기는지(요약? 최신? 내 일 관련?)가 없다. FR-2.5 의 「여기까지 정리」는 *사람이 누를 때만* 도는 수동 요약이라 자동 절단의 답이 아니다 |
| **⑤ 한 에이전트가 여러 방 · 각자 맥락 · 요청하면 다른 방 읽기** | FR-4.5(`colab room list/read`, 권한 2조건, 양쪽 기록, 턴당 상한), §3 용어표 Agent Context, §12 위험표 | **부분 — 구멍 3건** | **(a) `room_link`(참고 방 링크)를 방장이 거는 화면이 없다.** 권한 2번 조건이 "참여자 **또는** room_link" 이므로, 링크를 걸 자리가 없으면 **에이전트가 참여하지 않은 방은 영원히 읽을 수 없다** — ⑤의 핵심이 반쪽이 된다. **(b) 읽힌 쪽 흔적이 사실상 보이지 않는다**(§3 참조). **(c) 에이전트 맥락 분리는 데이터로는 성립하나 화면 표시 규칙이 없다** — 참여자 칩 상태(FR-1.3)는 task 에서 파생되고 task 는 워크스페이스 전역이라, 결제팀 방의 Writer 칩이 `working` 일 때 그게 **마케팅 방 일**일 수 있다. §10 v2.0 은 동시성 상한만 "v2 에서 같이 볼 것"으로 미뤘고 표시 문제는 언급이 없다 |

## 2. 화면 충격표 (S1~S17 + 신규)

`SCREEN.md` §3.2 의 17개를 v0.19 로 통과시킨 결과다. "없으면 못 하는 것" 은 **Director 요구 번호**로 이어 붙였다.

### 2.1 사라지는 화면

| 화면 | 판정 | 이 화면이 없으면 사용자가 무엇을 못 하는가 |

F2 지표(알림→제출 < 2분, "세션을 열지 않고 답한다")가 **일 밖 task 에서 깨진다** — 맥락 한 줄이 없으니 방을 열어야 한다 |

**시나리오 E 전체: 사람 클릭 12회 내외, 화면 이동 3회** **[추정]**. 클릭 수 자체는 무겁지 않다 — **문제는 12회 중 6회가 아직 존재하지 않는 화면 위에서 일어난다는 것.**

### 3-1. 일이 여러 개 열린 방에서 메시지가 어느 일에 속하는지 사람이 어떻게 아는가

**답이 PRD 에 없다.** 있는 것은 셋뿐이다: `message.work_id?`(칸), FR-2A.5 「메시지·lane 은 자기가 속한 일을 가리킨다(없으면 "일 없음")」(**읽는 쪽** 규칙), 「진행 중인 일」 칩(**방 상단** 표시). **쓰는 쪽 규칙 — 내가 지금 치는 메시지가 어느 일에 붙는가 — 이 통째로 비어 있다.** 가능한 설계는 셋이고 **[추정]** 결과가 서로 크게 다르다:

| 안 | 규칙 | 대가 |
|---|---|---|
| A | 작성창에 **일 선택 드롭다운**(기본: 마지막으로 연 일) | 잡담이 잡담이 아니게 된다 — 매번 "일 없음"을 고르는 부담. 시나리오 E-2 의 가벼움이 사라진다 |
| B | **스레드로만 귀속** — 일은 자기 스레드를 갖고, 메인 타임라인 메시지는 항상 일 없음 | 방이 "일 개수 + 1"개의 타임라인으로 쪼개진다. E-3 의 "같은 방에서 이어진다" 감각이 약해진다 |
| C | **멘션 대상의 현재 lane 이 속한 일로 자동 귀속** | 조용하고 자연스럽지만 **사람이 예측할 수 없다** — 트리거 미리보기(O4)가 "이 메시지는 @Writer 를 트리거합니다"에 더해 "**일 〈보고서〉에 들어갑니다**"까지 말해야 한다 |

**[추정] 권고: C + 트리거 미리보기 확장.** 이미 있는 장치(O4 칩) 위에 얹히고 E-2 의 가벼움을 지키는 유일한 안이다.

### 3-2. 일 밖 task 의 결과는 어디에 보이는가

**어디에도 없다.** 근거: (a) 우열 6칸 전부가 일 또는 방 설정(실측 스크린샷), (b) FR-4.3 아티팩트는 `work_id?` nullable 이라 일 없는 아티팩트가 생길 수 있는데 사이드바 목록의 그룹 규칙이 없음, (c) FR-4.2 결정 기록도 `work_id?` 로 같은 상태, (d) Inbox 카드의 맥락 줄이 goal 에 매여 있음(§2.2). **시나리오 E-2 의 "답이 방에 남는다"는 실제로는 "타임라인 메시지 하나로만 남는다"이고, 방이 계속 쓰이면 그 답은 스크롤 밖으로 사라진다.** 세션 모델에서는 세션이 곧 한 주제라 우열 6칸이 전부 관련돼 있었는데, 방에서는 **방 전체 크기의 사이드바가 일 하나만 비추게 된다.**

### 3-3. 방이 20개가 되면 무엇이 무너지는가

**PRD 가 이미 이 숫자를 적어 두었다.** §12 검토 항목: 「채널 계층 — 한 워크스페이스의 **활성 세션이 20개를 넘기 시작하면** 도입」, §10 v1.1: 「세션이 수십 개가 되면 평평한 목록으로는 탐색이 무너진다」. v0.19 는 방을 **세션 자리에 놓았을 뿐 그 위 계층을 만들지 않았으므로, 같은 붕괴가 방 목록에서 그대로 재현된다.** 게다가 방은 **완료되지 않아 목록에서 빠지지 않는다** — 세션은 `completed` 되어 필터로 걷혔지만 방은 `archived` 를 사람이 눌러야만 걷힌다. **20개 문제가 세션 때보다 더 나쁘다.**

구체적으로 무너지는 것 넷:

1. **카드로 훑어서 고르지 못한다.** 방 카드에 남는 정보는 이름·설명·마지막 활동 셋뿐(§2.2 S5).
2. **안 읽음 모델이 아예 없다.** `room_participant` 에 `last_read_at`/`last_read_message_id` 가 없고, `inbox_item` 에도 없다. 내비 뱃지는 **`action_required` 개수만 센다**(SCREEN §4.6: "info 까지 세면 뱃지가 무의미해진다"). 세션 모델에서는 세션이 끝나 사라지니 견뎠는데, **방은 끝나지 않으므로 "아직 안 본 대화"가 어디에도 뜨지 않는다.**
3. **§12.1 열린 항목 4** 가 이것을 정확히 인정한다 — 「방 목록이 늘어날 때의 기본 정렬·검색(마지막 활동순? 안 읽음 우선?) — R2 화면 전에 정한다」. **안 읽음 우선을 고르려면 위 2번의 데이터 모델이 먼저 있어야 하는데 §7 에 없다.**
4. **에이전트 동시성이 방을 가로질러 샌다.** Writer 가 20개 방에 있으면 `max_concurrent_tasks` 3 을 20개 방이 나눠 쓴다(§9·§12 위험표). 사용자에게는 "내 방의 Writer 가 이유 없이 느리다"로 보인다 — 사유 표시 없음(§3-6c).

### 3-4. 읽지 않은 것 표시·알림은 방 단위인가 일 단위인가

**PRD 가 답하지 않는다.** 확인된 사실만:

| 층 | 지금 상태 |
|---|---|
| **안 읽음** | **모델 자체가 없다**(위 3-3-2). FR-8 도 언급 없음 |
| **알림(인박스)** | `inbox_item(type, severity, **session_id**, ref_id, read_at)` — 방 id 만 있고 `work_id` 없음. FR-8 의 「세션 구독 설정: 전부 / HITL만 / 종료만」도 **방 단위로만 읽힌다**(§5 대응표: 인박스 알림 → 방) |
| **PRD 자신의 인식** | §10 v2.0 「**v2 에서 같이 볼 것**: … **방 단위 알림 설정**」 — v2.0(=v0.19 그 자체) 의 항목이 아니라 그 *뒤*로 미뤄져 있다 |

**결과: v0.19 를 그대로 구현하면 알림은 방 단위, 안 읽음은 없음.** 일이 5개 도는 방에서 "예산 승인해 주세요" 가 어느 일 것인지 인박스 카드가 말할 수 없다(`work_id` 없음). **[추정] 최소선: 알림은 일 단위(방으로 집계해 보여줌), 안 읽음은 방 단위.** 일 단위 안 읽음까지 가면 인박스가 일 개수만큼 부푼다.

## 4. 마법사 제거의 대가 — 모르고 지나쳐 사고가 나는 것

S6 7단계가 **강제로 사람 눈앞에 놓던 것**을 방 설정 기본값으로 내렸을 때 무엇이 조용해지는지. 왼쪽이 마법사가 하던 말, 오른쪽이 그 말이 사라졌을 때 실제로 일어나는 일이다.

| # | 마법사가 강제하던 것 | v0.19 의 기본값 | **모르고 지나쳐 나는 사고** | 사고 크기 |
|---|---|---|---|---|
| **W-1** | **3단계 격리** — `none`/`worktree` 선택 + "worktree 선택 시 workdir 바인딩 규칙(에이전트당 1개)을 **그림으로** 설명" | FR-2.3 `isolation` = 워크스페이스 기본 **`none`** | 개발용 방을 이름만으로 만들면 격리가 `none` 이다. `none` 의 workdir 바인딩은 **lane 당 하나**(FR-6.1)이지만 저장소 워크트리가 아니므로 **에이전트들이 실제 저장소 디렉토리에서 서로의 편집을 덮어쓴다.** 마법사에서는 3단계를 반드시 지나야 했다 | **치명 — 코드 유실** |
| **W-2** | **4단계 런타임** — "자동 선택(**첫 실행 시 고정**)" 이라는 **문장을 읽고** 고름. worktree 면 remote URL 일치 머신만 후보, 저장소 경로·클린 여부를 probe 로 검증해 표시 | FR-2.3 `runtime_id` = 없음 → **첫 task dispatch 때 고정** | **방에서 던진 첫 잡담 한 마디가 그 방의 머신을 영구 확정한다.** 그리고 S7 상단 액션 표가 못박는다 — 「런타임과 격리는 **변경 불가**(workdir 이 묶여 있다)」. 즉 **시나리오 E-2 의 "@Researcher 수수료 어때?" 한 줄이 결제팀 방의 컴퓨터·격리를 되돌릴 수 없게 결정한다.** 사용자는 자기가 무엇을 확정했는지 모른다 | **치명 — 되돌릴 수 없음** |

### 4-1. G8 실측(F1 15분, 5명)과의 관계

**세 가지가 동시에 일어난다. 두 개는 좋고 하나는 나쁘다.**

1. **시간은 확실히 줄어든다.** U1 은 13단계이고 **7~13단계(7개)가 전부 마법사**다. 방 만들기는 1단계(이름 한 칸)로 줄어 **13 → 7단계**가 된다. 통과 조건 「5명 중 4명이 15분 안에」는 더 쉬워진다.
2. **U1 자체가 재정의돼야 한다.** U1 의 목표는 「**세션 하나가 돌기 시작한다**」이고 13단계 도달 기준은 「S7 타임라인에 goal 시스템 메시지 1개, lane 보드 빈 상태, 참여자 칩 Lead `working`」이다. 방은 **만들어도 아무것도 돌지 않는다** — 누가 메시지를 쳐야 돈다. **새 기준선이 필요하다: 「방 만들기 + 초대 + 첫 멘션 → 에이전트 칩이 `working`」** **[추정]**.
3. **사후 질문 정답률 ≥ 80% 가 떨어진다 — 그리고 이것이 G8 의 실제 위험이다.** U16 의 사후 질문 3개 중 하나가 「**코드는 어디 있나요?**」(개발자만)인데, 그 답을 가르치던 유일한 화면이 **마법사 3단계(격리 선택 + workdir 바인딩 그림)** 다. 방 만들기 한 칸에서는 아무도 그것을 말하지 않고, W-1·W-2 에 따라 **그 답은 사용자가 모르는 채로 확정된다.** 즉 **G8 의 두 통과 조건이 반대 방향으로 움직인다 — 시간은 좋아지고 정답률은 나빠진다.** 실측이 "통과"로 나와도 §11 의 취지(사용자가 시스템을 이해한 채 15분)는 달성되지 않는다.
4. **이탈 신호 기준도 바뀐다.** U1 의 이탈 신호 중 「9~10단계에서 뒤로 가기 → 격리·런타임 설명 부족」은 **그 단계가 없어져 관측 자체가 불가능해진다.** 대신 **[추정]** 새 이탈 신호가 필요하다: 「방을 만든 뒤 30초 이상 정지」(빈 방에 할 일 안내가 없음, §1-①), 「설정 화면을 첫 메시지 전에 연다」(기본값을 신뢰하지 못함).

> |---|---|---|---|---|---|
> | **방장** | 방 | ✅ | ✅ | **일 밖 task 의 HITL** | ✅ |
> | **Director** | 일 | ✅ | ✅ | 그 일의 HITL | ❌ |
> | **deputy** | 일 | ✅ | ✅ | 기한 절반 경과 후 | ❌ |
> | **멤버** | 방 | `visibility` 에 따름 | 〃 | ❌ | ❌ |

### P0-5. FR-2.1 뒤에 새 항 — 첫 dispatch 고정을 사람이 알게 한다 (W-1·W-2)

> **`[v0.19]` FR-2.1.1 방을 만들 때 확정되는 것과 확정되지 않는 것.** 방 만들기가 칸 하나인 대가로, **사용자가 고르지 않은 값이 나중에 되돌릴 수 없게 확정된다.** 그 사실을 만들기 시점과 확정 시점 **두 번** 알린다.
>
> - 만들기 화면 아래에 한 줄: **「격리 없음 · 컴퓨터는 첫 실행 때 정해집니다 — 방 설정에서 미리 바꿀 수 있습니다」** (워크스페이스 기본값을 그대로 읽어 쓴다).
> - **첫 task dispatch 로 `runtime_id` 가 고정되는 순간**, 방 타임라인에 `system` 메시지를 남긴다: **「이 방은 〈컴퓨터 이름〉에서 돕니다. 격리 방식과 컴퓨터는 이제 바꿀 수 없습니다 — 작업 폴더가 거기 묶여 있습니다.」**
> - **저장소를 쓰는 방은 첫 dispatch 전에 격리를 고르게 한다.** 방 설정 `isolation` 이 `none` 인 채 **`repo_path` 가 있는 런타임으로** 첫 dispatch 가 일어나면 방장에게 HITL(`approval`)을 발행한다 — 「이 컴퓨터에는 저장소가 있습니다. 에이전트들이 **같은 폴더를 함께 고치게** 됩니다. 워크트리로 나눌까요?」. 기본 제안값은 `worktree` 다.

### P1-7. FR-3.1 뒤에 새 항 — 메시지의 일 귀속 (§3-1)

> **`[v0.19]` FR-3.1.1 메시지가 어느 일에 속하는가.** `message.work_id` 는 다음 순서로 정해지며, **사람이 보내기 전에 확인할 수 있어야 한다**(FR-3.6 트리거 미리보기와 같은 칩에 표시).
>
> 1. 사람이 작성창에서 명시적으로 고른 일 (고르면 그것으로 고정).
> 2. 그 메시지가 어떤 일의 스레드 안에 있으면 그 일.
> 3. 멘션 대상 에이전트가 이 방에서 **지금 실행 중인 lane** 을 가지고 있고 그 lane 이 일에 매여 있으면 그 일.
> 4. 위 어느 것도 아니면 **일 없음**(`work_id = null`).
>
> 에이전트 메시지는 자기 task 의 lane 이 매인 일을 따른다. **트리거 미리보기 칩은 트리거 대상과 함께 귀속될 일을 적는다** — 「@Writer 를 트리거합니다 · 일 〈보고서 초안〉에 들어갑니다」. 일 없음이면 그렇게 적는다.

### P1-8. FR-2A.5 에 붙일 문장 — 일 밖 결과의 자리 (§3-2)

> **FR-2A.5 끝에 추가**: 「**일 밖 실행의 결과도 방에 자리가 있다.** 방 사이드바는 **일 선택에 따라 바뀌는 칸**(goal·종료 조건 진행률·그 일의 비용)과 **방 전체 칸**(아티팩트·결정 기록·방 누적 비용·방 설정)으로 나뉘며, 일 밖 task 가 만든 아티팩트·결정도 **방 전체 칸에 「일 없음」 묶음으로** 보인다. 일을 고르지 않았을 때 사이드바 위쪽은 **최근 활동한 일**을 보여 주되 그 사실을 적는다. 아티팩트·결정 기록·비용은 `work_id` 가 nullable 이므로(§7) 목록은 일별로 묶고 **일 없음 묶음을 마지막에** 둔다.」

### P1-9. FR-4.5 에 붙일 문장 — 읽힌 쪽 가시성과 참고 방 링크 (§1-⑤a·b, 3-5a)

> **FR-4.5 「읽은 사실을 남긴다」 불릿을 대체**:
>
> 「**읽은 사실을 남긴다.** 읽기는 **양쪽 방**에 기록되며, **읽은 방**에는 그 task 의 `task_event`(`class=status`, 사람이 읽는 문장은 `payload.args.note`)와 방 활동에, **읽힌 방**에는 `activity_log` + **방 타임라인의 `system` 메시지 한 줄**로 남는다 — 「〈사람 이름〉의 요청으로 〈에이전트〉가 이 방을 읽었습니다(요약 + 최근 N건)」. 읽힌 방에는 그 task 가 없어 `task_event` 에 붙일 수 없고, **활동 로그 화면(S15)은 v1.1 이므로 시스템 메시지가 v1 의 유일한 가시 경로다.** 이 한 줄이 없으면 §12 위험표가 FR-4.5 의 완화책으로 내건 "양쪽 기록"이 절반만 작동한다.
>
> **거부도 사람에게 말한다.** 권한 두 조건 중 하나라도 어긋나 `403` 이 나면 그 사실을 **읽으려 한 방의 활동**에 남긴다(어느 방인지는 적지 않는다 — 존재를 숨기는 규칙 그대로): 「〈에이전트〉가 읽을 수 없는 방을 조회했습니다」. 사람이 "왜 안 되는지 모르는 침묵"을 겪지 않게 한다.
>
> **참고 방 링크(`room_link`)는 방 설정에서 방장이 건다.** 링크를 걸면 **링크된 양쪽 방 모두에 `system` 메시지**로 남기고(한쪽만 알면 유출 경로가 한쪽에만 보인다), 해제도 같다. 링크가 없으면 **에이전트는 자기가 참여한 방만 읽을 수 있다.**」

### P2-11. §12.1 에 열린 항목 추가 (Director 가 정할 것)

> 5. **방에 사람 초대 절차를 둘지** — FR-2.2 는 사람도 초대한다고 하고 FR-5.3 은 사람에게 초대 절차가 없다고 한다. `visibility: workspace | invited`(P0-1)로 둘 다 살릴지, 한쪽을 버릴지.
> 6. **읽지 않은 것을 무엇으로 셀지** — 방 단위(`room_participant.last_read_message_id`)인가 일 단위인가. 방은 끝나지 않아 세션 때와 달리 **목록에서 저절로 빠지지 않으므로**, 안 읽음 없이는 방 20개에서 훑기가 무너진다(§12 의 "활성 세션 20개" 판단이 방에 그대로 옮는다). 4번(정렬·검색)의 전제다.
> 7. **`FR-4.4` 컨텍스트 재사용을 유지할지** — 방이 지속되고 FR-4.5 로 다른 방을 읽는다면 "완료된 세션을 새 세션에 첨부"는 목적이 겹친다. 유지한다면 대상은 **보관된 방**이 되고, 버린다면 마법사와 함께 v1 범위에서 뺀다.
> 8. **화면에서 Work 를 무엇이라 부를지** — 지금 `COMPONENTS.md` §8.4 자물쇠가 **task 를 「할 일」로 못박았고**, S5 의 한 줄 설명은 **session 을 「일」이라 부른다**(「에이전트 팀에게 맡긴 **일 하나가 세션**입니다」). 여기에 v0.19 가 Work = **「일」**을 넣으면 **방 화면에 「일 3개 · 할 일 12개」가 나란히 뜬다.** 한 글자 차이로 상위·하위 개념을 가르는 말은 훑어서 구분되지 않는다. **[추정] 후보: Work 를 화면에서 「과제」로 부르고 문서의 「일」은 유지**, 또는 task 의 화면 말을 「실행」으로 바꾼다. 어느 쪽이든 §8.4 표와 `web/lib/wording.test.ts` 자물쇠를 함께 고쳐야 한다.
