## 1. 계획 원칙

1. **의존성과 리스크가 순서를 정한다.** 기능의 화려함이 아니다. ACP 하네스가 없으면 아무것도 안 돌고, 라우터가 없으면 lane이 의미 없고, 재개 경로가 없으면 HITL이 작업을 잃는다.
2. **수직 슬라이스를 먼저 끝까지 뚫는다.** 서버·데몬·웹 세 층을 각각 완성한 뒤 붙이면 통합에서 3주가 사라진다. 2주차 끝에 "멘션 하나가 런타임을 거쳐 답글로 돌아오는" 경로가 실제로 돌아야 한다. 그 뒤로는 그 경로를 넓히는 일이다.
3. **스파이크가 아키텍처를 정한다.** `claude-code-acp`가 불안정하면 CLI 어댑터가 v1에 들어오고 하네스가 두 벌이 된다(PRD §12-1). 이 결정 없이 2주차를 시작하지 않는다.
4. **데이터 유실 계열은 해당 단계 안에서 끝낸다.** 재개·재시도의 부분 실행 처리(FR-7.1), 고아 프로세스(FR-9.1), 워크트리 오염(§8.4)은 "나중에"가 없다. 그 기능을 켜는 단계에서 같이 만든다.
5. **인터페이스 계약을 코드보다 먼저 고정한다.** 서버 API, `task_event` 스키마, `colab` CLI 명령·토큰, 데몬↔서버 프로토콜. 세 스트림이 이것을 보고 병렬로 간다.
6. **컷 순서는 이미 정해져 있다**(PRD §10). 주차별 체크포인트에서 발동 여부만 판단한다. 즉석에서 범위를 고민하지 않는다.

## 2. 시스템 분해와 스트림

PRD §8.1의 구성을 따른다. 기술 스택은 **Go 서버 · Next.js 웹 · Postgres로 확정**했다(2026-09-04). 데몬과 `colab` CLI도 Go — 단일 바이너리 배포가 필수라 서버와 언어를 맞추면 프로토콜 타입을 공유할 수 있다.

| 스트림 | 구성 요소 | 주 언어 | 비고 |
|---|---|---|---|
| **S (서버)** | API, Router, 세션·lane·task 상태 머신, 큐(Postgres SKIP LOCKED), 실시간(WS/SSE), Platform LLM 호출, 인박스, GC 스케줄러 | Go | 동기 API 경로에서 LLM 호출 없음(§8.1) |
| **D (데몬)** | 페어링·probe, task claim, workdir 준비, 브리프 파일, **ACP 하네스**, (조건부) CLI 어댑터, `task_event` 전송, heartbeat, 고아 정리 | Go | 단일 바이너리. multica 데몬 구조 참고 |
| **C (colab CLI + MCP)** | `colab session/message/lane/hitl/artifact/decision/status/review` 명령, 같은 기능의 MCP 서버, `COLAB_TASK_TOKEN` 인증 | Go | 데몬과 함께 배포. 에이전트가 플랫폼에 되돌아오는 유일한 경로 |
| **W (웹)** | S1~S17 화면, 컴포넌트 8종, 실시간 갱신, 활동 피드 렌더러 | Next.js | `COMPONENTS.md`의 도메인 컴포넌트를 그대로 React 컴포넌트로 |

**병렬성.** P0에서 계약을 고정하면 P1부터 S·D·W·C를 **각각 별도 에이전트**가 동시에 만든다(§10). 각 단계의 DoD는 네 스트림이 붙은 상태에서만 판정한다 — 스트림별 "내 쪽은 됐다"는 완료가 아니다. 에이전트는 서로의 작업을 암묵적으로 알지 못하므로, **계약(§3 P0)이 사람 팀일 때보다 훨씬 더 중요**하다 — 계약이 곧 에이전트 간 대화다.

### P1 · 2~3주차 — 수직 슬라이스

**목표**: 사람이 `@Lead`를 멘션하면 Claude Code가 ACP로 돌고, `colab message post`로 답글을 올리고, 그것이 웹에 실시간으로 보인다. **lane·HITL·격리 없이** 이 한 경로만.

| 스트림 | 작업 |
|---|---|
| S | 워크스페이스·멤버 CRUD, 에이전트 CRUD(프로파일 1개), 세션 생성(`none` 격리·`runtime_id`·participants), 메시지 게시, **라우터 규칙 2·6만**(명시 멘션 → task, 그 외 → assignee), task 상태 머신 `queued → dispatched → running → completed/failed`, `task_event` 수신·저장, WS 브로드캐스트, `COLAB_TASK_TOKEN` 발급·검증 |
| D | task claim(long-poll), `none` workdir 준비, 브리프 파일(§8.4 [1]~[5] — 결정 기록·컨텍스트는 나중), **ACP 하네스 핵심**: `initialize` → `session/new` → `session/prompt`, `allow_once` 탐색으로 권한 자동 응답, `session/update` → `task_event` 정규화, `turn_end` 처리, 프로세스 그룹 관리, heartbeat 15초 | 
| C | `colab session get`, `colab session messages`, `colab message post`, MCP 서버 동일 3개 | 
| W | 앱 셸(S1 로그인, App Nav), S5 목록(최소), **S7 중앙 열만** — 타임라인 + 작성창(멘션 자동완성) + 활동 피드 **원본 레일**, 실시간 갱신 |

**DoD** (E2E 자동화)
- 웹에서 "@Lead 인사해줘" 게시 → 2초 안에 데몬이 claim → Claude Code가 ACP로 실행 → `colab message post`로 답글 → 웹 타임라인에 답글이 스트리밍 도착. p50 첫 출력 10초 이내(§9).
- 데몬을 `kill -9`하고 재시작하면 `running` task가 heartbeat 만료 후 재큐잉되고, 같은 메시지가 **두 번 게시되지 않는다**(idempotency `task_id + seq`).
- 취소(§8.2.2 절차)가 프로세스 트리를 남기지 않는다.

**왜 이것부터인가.** ACP 하네스·큐·실시간·CLI 토큰 — 이 넷이 나머지 전부의 기반이다. 이 단계에서 하네스의 추상화 누수(권한 옵션 형식, 이벤트 형식 차이)가 드러나야 P2에서 Hermes를 붙일 때 다시 짜지 않는다.

- **시나리오 A E2E**: Lead가 Researcher에 3항목 위임 → lane 3개 병렬 → 각각 완료 → **합류가 정확히 한 번** 발화 → Lead 종합 → Writer 초안. 이 흐름에서 Lead가 깨어난 횟수 = 위임 1 + 합류 1 + Writer 완료 통보 1.

**리스크**: 라우터 규칙이 12개 조합이라 골든 테스트 없이는 회귀를 못 잡는다. 테스트가 먼저다.

### P3 · 6~7주차 — HITL · 재개 · 예산

**목표**: 사람이 개입하는 모든 경로. 세션이 멈추고 다시 이어지되 **작업을 잃지 않는다.** 시나리오 C·D 통과.

| 스트림 | 작업 |
|---|---|
| S | HITL `question`·`approval`: 툴 호출 → `pending_hitl` → `turn_end`에 `waiting_human` 전이 → task당 1개 제한, 인박스 Needs Action 질의 + 심각도 7종, deputy(기한 절반 후 응답 가능, 취소는 즉시), `approval`은 절대 자동 진행 안 함 + `overdue`, **재개 = 새 attempt**(lane `runtime_session_ref` resume 우선 → 콜드 스타트), **재시도 공통 경로**(같은 workdir, `attempt ≥ 2` 프롬프트에 "이미 게시한 메시지 목록"), 재지시 = 새 task(`restarted_from_task_id`), 세션 `paused` 사유 5종 + 재개(드레인 vs 취소), `paused` 중 `queued` dispatch 금지, **턴 중 예산 강제** → `paused(budget)` + `task.budget_override`, 추정치 런타임은 하드 컷 대신 `paused`, 시스템 발행 HITL(`source: system`) |
| D | `usage_update` 누적 → 예산 초과 시 §8.2.2 취소, resume 거부 감지 → `resume_rejected` 보고, `<resumed>` 프롬프트 구성 |
| C | `colab hitl ask --default`, `approve-request`, `request-info` — 호출 시 "턴을 끝내라" 반환 |
| W | S8 인박스 전체(7종 + deputy 노출 시점), HITL 카드(타임라인·인박스), S7 상단 액션(일시정지·재개·종료·참여자·Director 교체), lane 카드 "중단하고 다시 지시"/"중단", `paused` 배너 5종, **S7-P·S7-D 변형**(권한 비활성 + 툴팁), task 이력 펼침 |

**DoD**
- HITL 왕복: Writer 질문 → 턴 종료(프로세스 없음, 슬롯 미점유) → Director 답변 → 새 attempt → **resume 성공 시 이전 대화를 기억**(스파이크 4 기준으로 검증) → 콜드 스타트 시에도 작업 이어감.
- **중복 0**: 파일 절반 편집 + 메시지 2개 게시 상태에서 데몬 kill → 재큐잉 → 재개 → 같은 메시지 재게시 0, 같은 편집 중복 적용 0. §11 지표 "< 1%"를 테스트로.
- 예산: task 예산 초과 → `paused(budget)` → Director 상향 승인 → 같은 lane·workdir로 재개. 에이전트 `budget_per_task`는 불변.

## 10. 개발 주체가 에이전트일 때 — 오케스트레이션 운영

이 제품은 "에이전트 여러 개가 공유 컨텍스트에서 협업하고 사람은 Director로 개입한다"는 모델이다. **개발 자체를 같은 모델로 한다.** 그래서 PRD가 정한 규칙 — 위임·합류·질문 경로·루프 상한·HITL — 이 개발 과정에도 그대로 적용된다. 잘 안 되는 지점이 곧 제품의 약점이므로, 개발 중 겪은 마찰은 PRD 리스크(§12)로 되먹인다.

### 10.1 역할

| 역할 | 수 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| **Director** (사람) | 1 | §8 결정, 스파이크 판정, 단계 DoD 승인, HITL 응답, 컷 발동, PR 최종 머지 | 코드 작성 |
| **Lead** (오케스트레이터 에이전트) | 1 | 단계별 작업 분해(§10.3), 스트림 에이전트에 위임, 합류 후 통합 상태 보고, 계약 변경 조율, 충돌 판단을 Director에게 HITL | 직접 구현 — PRD §8.3 Lead 프로토콜 그대로 |
| **S / D / W / C 에이전트** | 4 | 각자 스트림 구현. 워크트리 하나씩(격리), 작업 단위마다 PR | 남의 스트림 코드 수정 — 계약 변경이 필요하면 Lead에게 `blocked` |
| **Reviewer** | 1~2 | 모든 PR 리뷰: 계약 준수, 테스트 존재·통과, PRD/SCREEN 대조. 구현 에이전트와 **다른 모델**이 바람직 | 직접 수정 — 반려와 사유만 |
| **Integrator** | 1 | 단계 말에 네 스트림을 붙여 E2E(§5)를 돌리고 DoD 판정 자료를 만든다 | 기능 추가 |

Reviewer와 Integrator는 P1까지는 Lead가 겸해도 된다. P2부터는 분리한다 — 라우터 골든 테스트 이후로 리뷰 부하가 급증한다.

### 10.2 이 구성이 사람 팀과 다른 점

| 항목 | 사람 팀 | 에이전트 팀 | 계획에 미치는 영향 |
|---|---|---|---|
| 암묵 지식 | 복도 대화로 전파 | **없다** | 계약·SSOT 문서가 유일한 공유 컨텍스트. P0 계약 고정이 필수 조건 |
| 작업 단위 | 며칠짜리 티켓 | **반나절 이하**, 입력·출력·DoD가 명시된 것 | Lead가 §10.3 기준으로 분해. 큰 작업을 주면 스코프가 새거나 컨텍스트가 넘친다 |
| 병렬성 | 인원수 | 사실상 무제한 | 병목이 코딩 → **리뷰·통합·결정**으로 이동. Director가 하루 두 번은 인박스를 비워야 일정이 선다 |
| 실패 양상 | 느림 | **자신 있게 틀림** — 계약을 임의 해석, 테스트를 통과시키려 테스트를 고침 | Reviewer가 다른 모델, 테스트 파일 변경은 별도 PR로 강제 |
| 컨텍스트 한계 | 없음 | 있음 | 에이전트 브리프에 PRD 전체를 넣지 않는다. 해당 FR·계약·이 계획의 해당 단계만 |
| 일정 | 코딩 시간 | 리뷰 대기 시간 | §6 체크포인트에 "리뷰 적체 PR 수"를 추가 |

### 10.3 작업 단위 규칙

Lead가 위임할 때 지키는 형식이다. 이 형식을 못 채우면 작업이 아직 분해되지 않은 것이다.

```
작업: <한 줄>
스트림: S | D | W | C
입력: 읽어야 할 문서 절 (PRD FR-x.y, 계약 파일, 이 계획 §3 Px)
출력: PR 하나 — 변경 파일 범위, 새 테스트
DoD: 통과해야 할 테스트 이름 / 확인 명령
금지: 건드리면 안 되는 것 (남의 스트림, 계약 파일, 기존 테스트)
막히면: colab status set blocked — 계약 변경이 필요할 때
```

- **반나절 이하.** 넘으면 쪼갠다.
- **테스트를 먼저** — 라우터·상태 머신은 §5대로 골든 테스트를 별도 작업으로 먼저 위임한다.
- **계약 파일과 테스트 파일은 구현 PR에서 건드리지 못한다.** 바꿔야 하면 `blocked`로 Lead에게, Lead가 Director에게 HITL.

### 10.4 실행 구조

도구는 P0에서 확정한다(§8-6). 요구 조건만 적는다.

- **격리**: 스트림 에이전트마다 git 워크트리 하나. 모노레포에서 `server/` `daemon/` `cli/` `web/`를 각각 브랜치로. PRD FR-6.4의 worktree 격리와 같은 모델 — Orca 워크트리가 그대로 맞는다.
- **위임과 합류**: 단계 시작 시 Lead가 스트림별 작업을 fan-out, 전부 PR이 열리면 Integrator가 합류. 개별 완료마다 Lead를 깨우지 않는다(PRD FR-6.5).
- **질문 경로**: 구현 에이전트가 계약이 모호하다고 판단하면 임의 해석하지 말고 `blocked`. Lead가 답할 수 있으면 답하고, 제품 결정이면 Director HITL.
- **루프 상한**: 같은 PR이 리뷰 반려 3회면 자동으로 Director에게 올린다. 에이전트끼리 반려-수정을 무한히 돌지 않게.
- **리뷰 게이트**: PR 머지 조건 = Reviewer 승인 + CI 초록 + (계약·테스트 변경 시) Director 승인.
- **예산**: 단계별 토큰 예산을 두고 초과 시 Lead가 멈추고 보고. PRD FR-7.3과 같다.

### 10.5 단계별 에이전트 배정

| 단계 | Lead | S | D | C | W | Reviewer | Integrator |
|---|---|---|---|---|---|---|---|
| P0 | 계약 초안 작성·조율 | 스키마 v0, OpenAPI | 스파이크 1~6 **전담** | CLI 명령 표 | 토큰·배지 컴포넌트 | Lead 겸 | — |

| P2 | 분해·조율 | 라우터 전체·lane·합류·blocked | Hermes·프로파일 폴백 | 5개 명령 | S7 좌열·S6·S9·S10 | **분리** | **분리** |
| P3 | 〃 | HITL·재개·예산·상태 머신 | 예산 강제·resume 감지 | hitl 3개 | S8·S7-P·S7-D | 〃 | 〃 |

### 10.6 Director가 매일 하는 것

에이전트 팀에서 사람이 병목이므로 Director의 일을 정해둔다.

| 시점 | 일 | 근거 |
|---|---|---|
| 아침 | 인박스 — `blocked` 질문·HITL 응답. **30분 안에** | §11 지표 "HITL 응답 중앙값 < 30분"을 개발 과정에서 먼저 지킨다 |
| 정오 | 리뷰 적체 PR 머지 판정 | 계약·테스트 변경 PR은 Director만 |
| 저녁 | Lead의 통합 보고 확인, 다음 날 분해 승인 | |
| 단계 말 | DoD 판정, 컷 발동 여부(§6) | |

### 10.7 되먹임

개발 중 에이전트 협업에서 겪은 것을 PRD로 돌린다. 예상되는 것:

- Lead가 위임 후 턴을 끝내지 않고 기다리는 문제 → PRD §8.3 프로토콜 문구 강화
- 구현 에이전트가 계약을 임의 해석하는 문제 → "모호하면 `blocked`" 규칙의 효과 측정 → FR-6.2.1
- 리뷰 반려 루프 → FR-3.5 `max_pair_roundtrips` 기본값 재검토
- Director 응답 지연이 일정에 미치는 영향 → §11 지표의 현실성

이 되먹임이 제품 검증의 일부다. **자기 제품으로 자기를 만드는 것이 v1의 첫 사용자 테스트다.**
