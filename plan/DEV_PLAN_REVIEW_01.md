## 0. 총평

이 계획의 강점은 셋이다.

**의존성이 순서를 정한다.** "HITL 재개는 lane의 `runtime_session_ref`와 workdir 재사용 위에 선다. P2 없이 만들면 콜드 스타트만 되는 반쪽이 된다"(P3). "이 단계에서 하네스의 추상화 누수가 드러나야 P2에서 Hermes를 붙일 때 다시 짜지 않는다"(P1). 각 단계가 왜 그 자리인지가 문장으로 있다.

**DoD가 PRD 수치를 그대로 시험한다.** P1 "p50 첫 출력 10초"(§9), P3 "중복 0 — §11 < 1%를 테스트로", P2 "Lead가 깨어난 횟수 = 위임 1 + 합류 1 + 통보 1"(FR-6.5의 합류 1회를 숫자로). "됐다"를 사람마다 다르게 읽지 않게 하겠다는 목적을 지켰다.

**§10이 제품을 개발 과정에 적용한다.** "잘 안 되는 지점이 곧 제품의 약점이므로 마찰을 PRD 리스크로 되먹인다"는 관점은 v1의 첫 사용자 테스트를 개발 그 자체로 만든다. 사람 팀과 에이전트 팀의 차이표(§10.2)에서 "자신 있게 틀림 → Reviewer는 다른 모델, 테스트 파일은 별도 PR"로 대응을 연결한 것이 좋다.

약점도 셋이다. **작업량이 주차에 안 들어간다**(C1). PRD가 "10주는 빠듯하다"고 했는데 계획은 그 빠듯함을 주차별로 확인하지 않았다. **§10의 순환**(C2) — 개발을 `blocked`·합류·HITL로 돌리겠다는데 그것을 돌릴 `colab` CLI는 P1~P3에서 만든다. **P0에 스파이크 6건과 계약 3종과 스키마와 골격과 토큰이 한 주에 몰려 있다**(C3). 스파이크 1의 시간 상자가 3일인데, 그 결과가 계약(하네스 인터페이스)을 바꾼다.

## 2. Critical

### C1. 작업량이 주차에 들어가지 않고, 컷 판정이 너무 늦다

**P2(4~5주차)에 배정된 것**: 라우터 8규칙 + lane 해소 4규칙 + 병합 + 미리보기 API + lane/workdir 분리 + 합류 + `blocked` 경로 + 루프 상한 + 동시성 상한 4층 + 권한 게이트 + 결정 기록 (S), Hermes 어댑터 + 함정 3건 + 프로파일 다중·폴백 + 능력 판정 + 브리프 완성 (D), 명령 5개 (C), S7 좌열·우열 + 작성창 + 질문 카드 + S6 + S9 + S10 (W). 그리고 라우터 골든 테스트를 **구현보다 먼저**(§5). PRD v1 체크리스트 17항목 중 5항목이 여기 있다.

**P3(6~7주차)**: HITL 전이·제한·인박스 7종·deputy·overdue·재개(resume + 콜드)·재시도 공통 경로·재지시·paused 5종·dispatch 금지·예산 강제·budget_override·시스템 HITL (S), 예산 취소·resume 감지·`<resumed>` (D), hitl 3개 (C), S8·HITL 카드·상단 액션·lane 버튼·배너 5종·S7-P·S7-D·task 이력 (W). 게다가 "중복 0" 테스트는 부분 실행 시뮬레이터(§5)를 먼저 만들어야 한다.

에이전트 병렬성이 높다고 해도 **DoD는 네 스트림이 붙은 상태에서만 판정**(§2)하므로 통합 시간은 줄지 않는다. P2·P3 각각 3주가 현실적이고, 그러면 P4가 10~11주차로 밀려 worktree는 사실상 컷된다.

**컷 체크포인트가 늦다.** §6에서 컷 1은 1주차 말(스파이크 1 조건부), 컷 3은 7주차 말, 컷 2는 9주차 말이다. 그런데 컷 1의 대상(활동 피드 5클래스)은 P4 W에 있다 — 1주차에 예약해도 8주차까지 아무것도 안 줄어든다. 컷 2의 대상(자동 종료)도 P4다. **컷 세 개가 전부 P4를 겨냥하므로 P2·P3가 밀려도 컷으로 회복할 수 없다.**

**권고.**
- P2·P3를 각 3주로 다시 잡고(총 12주), 아니면 지금 컷 1을 **선제 발동**해 활동 피드를 P4에서 빼고 P4를 1주로 줄인다. PRD 컷 표는 "일정이 모자랄 때"라고 했는데, 계획 단계에서 이미 모자란다.
- 체크포인트에 **P2 중간(4주차 말)**: 라우터 골든 테스트 통과 + 시나리오 A 단일 런타임 통과. 미달이면 Hermes를 P3로 이월(이미 5주차 말에 있는 판정을 1주 당김).
- §6에 "리뷰 적체 PR 수"를 넣겠다고 §7-4에서 말했는데 표에 없다. 임계값(예: 미리뷰 PR > 8)을 적는다.

### C2. §10 오케스트레이션이 아직 없는 도구 위에 서 있다

§10은 개발 과정에 PRD 규칙을 그대로 적용한다: 구현 에이전트는 계약이 모호하면 `colab status set blocked`(§10.3), Lead는 위임 후 합류를 기다리고(§10.4 "개별 완료마다 깨우지 않는다"), 반려 3회면 Director HITL(§10.4), 단계별 토큰 예산(§10.4). 그런데:

- `colab status set blocked`는 **P2 C**에서 만든다. P0·P1에서 구현 에이전트가 `blocked`할 수단이 없다.
- 합류 1회 발화는 **P2 S**다. P0·P1의 Lead는 합류를 기다릴 수 없다.
- HITL은 **P3**다. 반려 3회 → Director HITL은 P0~P2에서 성립하지 않는다.
- 토큰 예산 강제는 **P3**다.

§8-6에서 "오케스트레이션 도구는 P0에서 확정(Orca vs 스크립트)"이라고 했으므로 **P0~P3는 외부 도구(Orca 오케스트레이션의 ask/reply·task DAG 등)로 돌리고, 제품이 그 기능을 갖추는 시점부터 자기 제품으로 갈아탄다**는 것이 실제 계획이어야 한다. 지금 §10은 그 전환 시점을 말하지 않아서, 읽는 사람은 "P0부터 colab으로 개발한다"로 오해한다.

**권고.** §10.4 앞에 표 하나: 단계별로 위임·질문·합류·HITL·예산 각각을 **무엇으로 돌리는가**(P0~P1: Orca / P2: 위임·합류·blocked는 colab, HITL은 Orca / P3~: 전부 colab). 그리고 "갈아타는 것 자체가 dogfooding 검증"이라고 적는다. 갈아탈 때 어떤 마찰이 났는지가 §10.7 되먹임의 첫 데이터다.

### C3. P0 한 주에 스파이크 6건 + 계약 3종 + 스키마 + 골격 + 토큰이 들어 있고, 스파이크가 계약을 바꾼다

P0 D 에이전트가 스파이크 6건을 전담하고 그중 1번의 시간 상자가 3일이다. 나머지 5건이 2일. 그런데 **스파이크 1의 결과(`transport: "cli"` 포함 여부)와 스파이크 2·3의 결과(툴 차단 방식, 브리프 전달 경로)가 하네스 인터페이스와 데몬↔서버 프로토콜을 바꾼다.** 계약을 스파이크와 같은 주에 고정하면 둘 중 하나는 다시 쓴다. §1 원칙 5("계약을 코드보다 먼저")와 원칙 3("스파이크가 아키텍처를 정한다")이 같은 주에 충돌한다.

**권고.** P0을 **1주 + 3일**로 늘리거나, 계약 고정을 "스파이크 1·2·3 판정 후"로 순서를 명시한다. 스파이크 4(P3 전으로 이동, §1.2)·5(P4 전으로 이동 가능 — worktree 종속)·6(반나절)을 P0에서 빼면 D 에이전트의 P0 부하가 절반이 된다. 스파이크 5는 컷 3이 발동하면 아예 필요 없다.

## 3. Major — 단계 배치 수정

### O1. Runtimes 화면(S11) 없이 P0 DoD를 판정할 수 없다

P0 DoD: "데몬이 서버에 페어링되어 `probe()` 결과가 DB에 들어감." 확인 수단이 DB 조회뿐이다. S11·S12는 P4다. P1 W에 S11 최소(카드 + CLI 목록 + 온라인)와 S12(설치 명령 + 연결 대기)를 넣는다. F1의 최대 이탈 지점(SCREEN §3.3)이 S12인데 P4~P5에서 처음 만들면 실측(P5)이 한 번뿐이다.

### O2. 팀 템플릿이 P5인데 F1 15분의 전제다

SCREEN §4.2: "3단계에서 템플릿을 전면에 둔다. 에이전트를 하나씩 만들게 하면 15분을 못 맞춘다." 템플릿(FR-1.4)은 역할·instruction 프리셋 3종 + 프로파일 자동 매핑이다. P2 W(S9·S10)와 함께 만들면 P2 DoD 시나리오 A 셋업도 빨라진다. P5는 마감이지 기능 추가 자리가 아니다.

### O3. 종료 조건 판정이 P4인데 시나리오 A(P2)·C·D(P3)가 종료를 요구한다

시나리오 A의 마지막 단계는 "`artifact_submitted` 충족 → 플랫폼이 `user_approval` HITL 발행 → 승인 → `completed`"다. P2 DoD가 "Writer 초안"에서 끝나므로 형식상 통과하지만, 세션 상태 머신 `active → completing → completed`가 P4까지 없다. **종료 조건 판정(4종 AND/OR)은 P2 S로, 요약 생성(Platform LLM)만 P4에 남긴다.** 판정은 라우터와 같은 결정적 로직이고 골든 테스트 대상이다. 컷 2는 "자동 종료 + 요약"을 `manual`로 바꾸는 것인데, 판정이 P2에 있으면 컷 2의 절감폭이 "요약 생성"으로 줄어든다 — 컷 표를 갱신한다.

### O4. 고아 프로세스 정리는 P1이다

FR-9.1(pgid 기록, 재시작 시 정리, 재큐잉 시 토큰 폐기)은 workdir 종류와 무관하다. `none` 격리에서도 데몬이 죽으면 런타임이 살아남아 `colab message post`를 계속 한다. P1 DoD에 이미 "`kill -9` 후 같은 메시지 두 번 게시 안 됨"이 있는데, 그것을 보장하는 것이 토큰 폐기다. 원칙 4대로 P1 D에 넣고, P4에는 "worktree에서의 이중 쓰기 검증"만 남긴다.

### O5. 활동 피드 렌더러의 단계가 컷 1과 어긋난다

P1은 원본 레일, P4가 중추 5클래스다. `task_event` 정규화(class·verb·object_ref·outcome)는 P1 D에서 하므로 서버에는 데이터가 있다. **렌더러 5클래스를 P2 W로 당기고**, 컷 1은 "P2에서 5클래스 대신 2클래스 + 오류"로 정의한다. 그래야 1주차 말 컷 1 예약이 실제로 P2 작업량을 줄인다.

### O6. 라우터 골든 테스트 "먼저"의 위치

§5 "라우터·상태 머신 테스트는 구현보다 먼저"인데 P2 S 작업 목록에 라우터 구현과 테스트가 같은 칸에 있다. §10.3이 "골든 테스트를 별도 작업으로 먼저 위임"이라 했으므로 P2를 **P2a(골든 테스트 작성, 3일) → P2b(구현)**로 나눠 적는다. 테스트는 Reviewer 에이전트가 쓰면 구현 에이전트와 해석이 갈리는 지점이 먼저 드러난다.

### O7. §10 자체가 PRD 규칙과 다른 곳

§10은 "PRD 규칙이 개발에도 그대로"라고 했지만 두 곳이 다르다.

| §10 | PRD | 비고 |
|---|---|---|
| §10.4 "반려 3회면 Director" | FR-3.5 `max_pair_roundtrips` **5** | 개발에서 3이 맞다면 그것이 되먹임 데이터다(§10.7 마지막 항목). 지금 값이 다른 이유를 적는다 |
| §10.1 Reviewer "직접 수정 안 함 — 반려와 사유만" | FR-3.4 lane 카드 "중단하고 다시 지시" | Reviewer 반려 = 재지시(새 task, `restarted_from_task_id`). 이 대응을 적으면 리뷰 루프가 task 이력에 남는다 |

그리고 §10.1 "Reviewer는 구현 에이전트와 다른 모델이 바람직"은 PRD 목표 6(벤더 혼합)의 개발 과정 검증이다 — Hermes 프로파일을 Reviewer에 쓰면 P2 Hermes 어댑터가 곧 실사용된다. 명시할 가치가 있다.
